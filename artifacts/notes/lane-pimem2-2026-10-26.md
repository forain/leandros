# lane/pimem2 — openbugs L8.8 follow-ups, 2026-10-26

## 1. Kernel GiB mapped at 2 MiB on direct boot — FIXED (QEMU-guarded, Pi unrun)
- entry_aarch64.s: after the L1 blocks, the GiB holding the running image
  (`adr .` >> 30, so RAM GiB 0 on a Pi 5, GiB 1 on QEMU virt) is remapped through
  an L2 table in early_pgtables page 2: 512 x 2 MiB blocks, same attributes.
  `a64_bbm` now refuses only the 2 MiB blocks holding code/stack/table.
- Guard: `scripts/test-direct-nomap.sh` — direct boot (bare ELF), packed virt DTB via
  `-dtb` (QEMU's generated 1 MiB DTB does not fit below 0x40080000, so a bare ELF
  otherwise gets no DTB/cmdline), `mm.nomaptest=0x50003000-0x50400000` in the kernel's GiB.
  A/B: unfixed `cleared 0 split 0 left 0x3FD000 -> STILL MAPPED (1022 probes)`;
  fixed `cleared 510 split 1 left 0 -> unmapped`.
- Open (Pi): check `[early] nomap:` shows `left 0` for the firmware no-map ranges.

## 2. SDHCI / GENET / RP1 DMA sync points — REFUTED (nothing to sync)
- drivers/src/sdhci.rs is polled PIO only: data moves through REG_BUFFER_DATA (0x20);
  Transfer Mode is only ever TM_BLOCK_COUNT_EN | TM_DIR_READ (DMA enable bit 0
  never set), no ADMA descriptors, no SDMA address. No DMA buffers exist.
- No GENET (Pi 4) or RP1/Cadence (Pi 5) ethernet driver exists in the tree
  (docs/hardware/raspberry-pi-5.md: RP1 behind untrained PCIe). xHCI remains the
  only DMA driver reachable on a Pi, already synced via DmaBuf.
- Whoever adds SDHCI ADMA2 or a GENET/RP1 driver must call DmaBuf::sync_for_device
  before the doorbell / command and sync_for_cpu before reading RX data/descriptors.

Regress aarch64: PASS. Direct-nomap guard: PASS. x86_64 builds.
