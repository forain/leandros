### Safety model (three layers)
1. Driver: without `nvme.rw=1` it never sends Write/WriteZeroes/DSM/Format/Flush;
   `write_sectors` returns `BlkErr::ReadOnly` (logs once). Admin opcodes used:
   Identify, Get Log (SMART), Get/Set Features (NumQueues, APST disable, PS0 —
   volatile, SV never set), Create/Delete I/O SQ/CQ. CC.SHN at power-off (no data change).
2. Registry: `read_only()` disks refuse all writes before the driver.
3. VFS/mount: EROFS on write(2); rw mount refused; `mount -r` gives a read-only f2fs mount.
Root: NVMe class is "nvme", `removable()=false`, so auto `/dev/root`
(removable || sd) never picks it; only explicit `root=` could.

### Cmdline
`nvme.rw=1` (allow writes), `nvme.apst=keep`, `nvme.shutdown=0`, `nvme.disable=1`.

### What to grep in the stick log (`[NVME]` lines)
`controller(s); mode`, `CAP`, `VS ... as found`, `controller disabled/enabled in`,
`Identify (... us): model ... serial ... firmware`, `MDTS`, `PS<n>:`, `APST`,
`power state`, `SMART:`, `I/O queue pair 1 created`, `nvme0n1: ... sectors`,
`registered as block device`, `GPT/MBR`, `nvme0n1pN: ... filesystem ...`,
`ready in N ms`, any `TIMED OUT` / `fatal status` / `write refused`, and at
power-off `I/O since boot` + `shutdown complete`.

### Pitfalls / refuted premises
- aarch64 HVF: never `read_volatile`/`write_volatile` on MMIO in this driver
  (ISV=0 crash). Queue memory (RAM) volatile is fine.
- EDK2 on aarch64 left the NVMe with PCI command 0 and CC.EN 0; x86 OVMF has an
  NVMe driver and will likely leave CC.EN=1 — that exercises the reset path.
- Interrupts: deliberately polled (aarch64 has no ITS; MSI-X logged only).
- Single in-flight command per controller (KMutex); fine for a non-root disk.
- Not done: MSI-X, multiple I/O queues, controller reset/recovery after a
  timeout (controller is marked dead → EIO), metadata/PI namespaces (skipped).
- USB `UsbDisk` intentionally does NOT implement `read_only()` (would make a
  write-protected-reporting stick refuse an rw root mount; behaviour change).
