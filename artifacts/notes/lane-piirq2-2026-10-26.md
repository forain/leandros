# lane/piirq2 2026-10-26 (openbugs #101: Pi 5 uart10 RX IRQ never fires): desk check of the firmware hand-off

Result: REFUTED (firmware side). The Pi 5 firmware hands off to our kernel exactly as it hands off to Linux. Nothing
on the card can change the GIC state the kernel inherits. No card change was made. The cause is on the kernel side or
in the PL011/GIC wiring, and the `[uartirq]` dump from d4a3ac3a decides between the remaining hypotheses (ranked below).

## Hand-off facts
- `target/final-aarch64/kernel-direct.bin` already carries an arm64 Linux Image header: `ARMd` at 0x38,
  text_offset 0, image_size 0xca0130, flags 0xa (4K pages, placeable anywhere). The firmware already treats it as a
  Linux Image (DTB in x0). The "add an Image header" idea is moot.
- Direct-boot config.txt (scripts/prepare-rpi5-sdcard.sh): `arm_64bit=1`, `kernel=kernel.img`, `kernel_address=0x200000`
  (the address the firmware uses for its own kernel_2712.img), `initramfs ... 0x10000000`, framebuffer_*,
  `enable_uart=1`, `uart_2ndstage=1`. No `armstub=`, so the firmware's built-in bl31 runs.
- bl31 (raspberrypi/arm-trusted-firmware master, plat/rpi/common/rpi4_bl31_setup.c, shared by rpi4 and rpi5):
  `bl31_platform_setup()` calls `gicv2_driver_init; gicv2_distif_init; gicv2_pcpu_distif_init; gicv2_cpuif_enable`
  **unconditionally**. `rpi4_gic_data` has no interrupt_props, and rpi5 `plat_rpi_bl31_custom_setup` is empty. So
  `gicv2_spis_config_defaults` writes IGROUPR=~0 for every SPI: all SPIs are Group 1 NS. No step depends on the image
  type, os_check, kernel_address or arm_64bit. The image type only selects the kernel entry and DTB pointers
  (stub_magic, kernel_entry32, dtb_ptr32). The old Pi 4 armstub8.S `setup_gic` likewise set all IGROUPR to ~0
  unconditionally.
- Entry EL: bl31 ERETs to EL2. entry_aarch64.s handles EL3->EL2->EL1. If we had entered at EL3 (no bl31), the timer PPI
  would also be Group 0 and dead. The timer works, so bl31 ran and SPI 153 is Group 1.
- We never write IGROUPR on v2. From NS it is RAZ/WI, so **the dump's `grp` field always reads 0 on the Pi and carries
  no information** (lane-piirq's "grp reads 0 confirms Group 0" does not hold).

## Ranked hypotheses for the next Pi capture (`[uartirq] init` and `[uartirq] rx-pending`)
1. **The PL011 never asserts its output, or the RX bytes are drained before it does.** Confirm: rx-pending shows
   `imsc 50`, `fr` with RXFE (bit4) clear, but `ris`/`mis` bits 4|6 = 0, and `pend 0`. The next step would be a UART-side
   check: IFLS, LCRH.FEN, and whether `cr` has RXE (bit9) and UARTEN (bit0) set. If `mis` != 0 but `pend 0`, see 2.
2. **The line does not reach GIC INTID 153.** This covers both a SoC wiring/mux difference and a GIC that has no INTID
   153. Confirm: `mis` bit4 or bit6 set with `en 1`, `tgt` = BSP mask and `pend 0`. Also check `D.typer`: bits[4:0]
   must be >= 4, or INTID 153 is not implemented. Expect bit10 (SecurityExtn) = 1.
3. **The GIC presents the interrupt but the CPU does not take it.** Confirm: `pend 1 en 1` and `C.hppir 99` (0x099). Then
   look at `C.rpr`: anything other than 0xff in task context means an un-EOI'd active interrupt is blocking it, and `act`
   would show it. Also check `C.ctlr` bit0 and EL.
4. **Wrong target.** Confirm: `tgt` is not the BSP's own ITARGETSR0 byte. BCM2712 core 0 might not be CPU interface 0,
   or a later AP rewrote V2_IFACE/affinity. pend 1 with hppir 3ff on the BSP points here too.
5. **Group 0 after all** (only possible with a non-stock firmware/armstub). Confirm: at init `en 0`, `prio 00` and
   `tgt 00` even though we wrote them (NS RAZ/WI), and `C.hppir 3fe` while the line is pending. `grp` reads 0 either way.
