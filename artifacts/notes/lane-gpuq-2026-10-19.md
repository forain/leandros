## Host GPU hang in STRESS_TWO_PROCS (root cause)
- The test's abandoner submitted `RING_IDX` ring 0 on an implicit virgl context (num_rings
  clamped to 1, so we forwarded it) and then closed with those fences in flight. QEMU
  virgl and vrend then stopped answering every fence. This happened in 2 of 3 runs: once as
  "HOST GPU HUNG ... wrote off 35", and once as a 300 s guest wedge behind a synchronous
  VIRTIO_GPU holder.
- Bisect: with the fence_is_done floor and wake change disabled, the hang still reproduced,
  so that change was not the cause.
- Upstream refuses this submission, which is fix (a). The abandoner now submits plain fenced
  work, the way a killed Mesa virgl client leaves it. With that, the stress passes with no
  hang, parked 0 -> 0.
- The earlier OUT_SYNCOBJ_INSTALLED EINVAL was a downstream effect: after the hang the
  submit itself failed (rc=-1), so nothing was installed. It passes now.

## Open
- A CONTEXT_INIT(virgl, NUM_RINGS=1) client can still send ring-0 RING_IDX fences, and
  closing such a context with fences in flight probably hangs the host the same way.
  Upstream allows this. No real client does it (Mesa virgl never sets RING_IDX).
  Consider refusing RING_IDX on the virgl capset entirely.
- submit_locked's bounded wait (CTRLQ_WAIT_ITERS) is long enough that a dead host
  wedges the guest's other CPUs for minutes behind a cursor or flush holder.
- Parallel QEMU runs from the same worktree with different RUN_IDs fail to boot (shared disk image).
