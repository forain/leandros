# lane/r8169 — 2026-10-09 — Realtek RTL8111/8168 Ethernet for the real PC

Branch `lane/r8169`, base main `d0061ae`. Not pushed. Goal: Ethernet on the
user's Kaby Lake PC (NIC `10ec:8168` at `05:00.0`, BAR2 `0xf7104000` MMIO,
BAR4 MSI-X table, per `nvrm-boot*.log`) so Firefox can reach YouTube.
The exact chip revision is not known yet: the first boot of this stick logs
it (`[r8169] ... chip <name> XID <xid> MAC version <n>`).

### Driver flow

1. **`init` (kernel init, boot context)**: finds the first `10ec:8168/8161/8136/8169/8167`;
   D3→D0; ASPM off in the NIC's Link Control; memory + bus master; maps the
   first memory BAR (UC); reads TxConfig → XID → MAC version (Linux's
   `RTL_GIGA_MAC_VER_xx` numbering, so reports can be compared with the
   reference tables); DASH check; `init_rxcfg`, IRQ mask+ack,
   8168g+ MAC hand-over from the OOB firmware (`hw_initialize`), chip reset,
   PMCH PLL bits; MAC from ERI 0xe0/0xe4 (8168e-vl+) or IDR0-5, random
   locally-administered as last resort; rings (256+256 descriptors, 2 KiB
   buffers, all below 4 GiB); MSI (x86_64; unmasked only for LinkChg / RX
   overflow / errors — the data path is polled); starts `[r8169]`.
2. **`[r8169]` thread**: if the chip has a PHY patch and `r8169.fw` is not 0,
   waits up to 30 s for the real root and loads
   `/lib/firmware/rtl_nic/<name>.fw`; then `up()` = DASH driver-start, PHY
   resume, per-chip PHY config (firmware first, as Linux), PHY soft reset,
   `cleanup` (RX gate, chip reset), rings re-armed, `hw_start` (per-chip MAC
   tables for 8168b/c/cp/d/dp/e/e-vl/f/8411/g/gu/8411b/h/ep), EEE off
   (MAC TX-LPI and PHY advertisement), autonegotiation (10/100 H/F, 1000 F,
   pause). Then it polls PHYstatus every 250 ms: link up/down lines, a full
   MAC+PHY register dump at 10 s / 30 s / 120 s without link, and a TX
   watchdog (frames in flight with no completion for 5 s → chip reset).
3. **data path**: `netdev::poll_receive` / `send_packet` from the net server
   (same 100 Hz cadence as virtio-net). RX: one frame per call, errored and
   fragmented (oversize) frames are counted and recycled. TX: copy into the
   slot buffer, pad to 60 bytes, OWN|FS|LS, TxPoll NPQ; slots reclaimed on
   every send and poll, and the doorbell re-rung while frames are pending.

Per-chip PHY tables: 8168g (VER 40), 8168gu/8411b (42-44), 8168h/8107e
(46/48). Other revisions: generic PHY path + firmware (if any), and the log
says `no per-chip PHY table`. Not done: 8125/8126 (2.5G, other PCI ids),
8411b MAC MCU patch, 8168d conditional firmware, checksum offload/TSO/jumbo,
INTx on x86_64 (no `_PRT`: falls back to polling), aarch64 MSI (no ITS).

### Kernel command line

`r8169.disable=1`, `r8169.fw=0|1|auto` (auto default; 1 = wait 120 s for the
root), `r8169.msi=0`, `r8169.eee=1` (keep EEE), `r8169.speed=100` (no
gigabit advertisement), `r8169.debug=1` (register dumps on link events),
`net.test=1` (init runs `/bin/net-autotest`).

### `/proc/net/nic`

`key: value` lines: driver, pci, chip, xid, mac_version, phy_id, firmware,
mac, running, link, speed, duplex, flow_control, phystatus, link_changes,
irq, irq_count, rx/tx packet/byte/error counters, ring indices, hardware
tally counters (`hw_tally: ... rx_missed ...`), then ifname, dhcp
(bound/searching), address, gateway, dns, dhcp_restarts, stack counters.
On QEMU: `driver: virtio-net` and `realtek: none`.

## Decision tree for failures

- **No `[r8169] found` line**: the PCI scan did not list `10EC:8168`
  (compare the `[PCI] Found dev` lines) or `r8169.disable=1`.
- **`TxConfig reads all-ones`**: BAR not decoded / device not in D0. Check
  the `PCI power state` line; try a cold boot (power off fully).
- **`UNKNOWN revision`**: send the XID; the generic path still runs.
- **`firmware: ... not loaded / rejected`**: harmless by itself. If link
  then fails, compare with `r8169.fw=0` (and vice versa).
- **`no link after 10 s: ... | PHY 00=.. 01=.. 05=.. 0a=..`**:
  - BMSR (01) bit 2 = link, bit 5 = autoneg complete; LPA (05) = 0000 means
    the partner was never heard: cable/port, switch LEDs, or the PHY is
    powered down (BMCR 00 bit 11 = 0x0800) → report the dump.
  - LPA non-zero but no link: try `r8169.speed=100` (cable pairs), then
    `r8169.fw=0`, then `r8169.eee=1` (unlikely), `r8169.debug=1` for dumps.
- **link up, `dhcp: FAIL`**: look at the counters lines.
  - `tx_packets` grows but `hw_tally tx_ok 0` → TX DMA not happening (bus
    master, TxPoll, descriptor address); `rings: tx_in_flight` stuck >0 and
    `TX timeout` lines confirm it.
  - `hw_tally rx_ok` / `rx_broadcast` grow but driver `rx_packets 0` → frames
    reach the MAC but not memory: RX descriptors/DMA (IOMMU left on by the
    firmware would look like this) — report `rings:` and `hw_tally:`.
  - `rx_packets` grow, `stack_rx` grows, no lease → DHCP server/VLAN; try
    another port. `dhcp_restarts` should be ≥ 1 after link up.
- **DHCP ok, DNS fails**: `resolv.conf|` lines; UDP to the router's DNS.
- **DNS ok, tcp443/http fail**: TCP path; check `ping` too (ICMP may be
  filtered by the router, so ping alone is not decisive).
- **RX hang after a while** (counters stop, `hw_tally rx_missed` rising,
  `irq_count ... rx_overflow` rising): the RX ring stopped being refilled or
  the chip stalled — report `/proc/net/nic`; TX hangs reset the chip by
  themselves (`resets:`), RX hangs do not yet.

## Risks

- Untested on hardware (QEMU has no RTL8168 model). The register sequences
  follow the reference drivers closely for 8168g/h; other revisions are
  less exercised.
- Polled data path: ~100 Hz service; worst-case latency 10 ms, RX ring of
  256 frames per poll (~38 MB/s ceiling); TCP is bounded by the 64 KiB
  window anyway.
- `request_firmware` reads f2fs from the driver thread after the root
  mounts; link waits for that (≤ 30 s, normally a few seconds).
- MSI target is the BSP only; INTx is unsupported on x86_64 (polling).

Found and fixed during the QEMU run: the first `tcp443` attempt at boot timed
out on one YouTube front-end address (a rerun connected in 35 ms), so the

`Deconfigured` was being counted as a lost lease.

about the hardware; the polled design's ceiling is the 64 KiB TCP window per
round trip (about 26 Mbit/s at 20 ms RTT), well above what YouTube needs.
