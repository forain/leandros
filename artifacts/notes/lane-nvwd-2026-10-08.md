# lane/nvwd — 2026-10-08 — the false channel kill on the first NVK run

Branch `lane/nvwd`, based on main `4ddde6a` (lane/nvuapi merged). Not pushed.
Input: `nvrm-boot3.log`, the first RTX 3070 run of NVK (M5 passed:
`nvktest info: PASS ... "NVIDIA GeForce RTX 3070 (NVK GA104-A)"`).

## 1. What the log showed

```
CHANNEL_ALLOC -> channel 2 (... token 0x4, fence ctx 3)
CHANNEL_ALLOC -> channel 3 (... token 0x5, fence ctx 4)
EXEC channel 3 pushes 1 waits 0 (gpu 0) sigs 1 -> seq 1 GP_PUT 2
+27800ms ERROR channel 2 of open 3: RM error notifier fired: info32 0x4 ..., status 0x0 -- channel killed (Xid lines so far 0)
+27800ms ERROR channel 3 of open 3: RM error notifier fired: info32 0x5 ..., status 0x0 -- channel killed
nvktest fill: FAIL (vkQueueSubmit -> VK_ERROR_DEVICE_LOST)
```

info32 equals each channel's work-submit token, there are no Xid lines, and
a real RC error would have status 0xffff. The kill was false.

## 2. Root cause (RM 570.86.16 source)

- `NVC36F_CTRL_CMD_GPFIFO_GET_WORK_SUBMIT_TOKEN` does more than return the
  token. `kchannelCtrlCmdGpfifoGetWorkSubmitToken_IMPL`
  (`src/nvidia/src/kernel/gpu/fifo/kernel_channel.c:3413`) ends with
  `kchannelNotifyWorkSubmitToken` (:4202), which calls
  `kchannelUpdateNotifierMem(index = notifyIndex[WORK_SUBMIT_TOKEN], info32 =
  token, info16 = 0, status = IN_PROGRESS|0x7fff = 0xffff)` (:1900). That
  writes a timestamped NvNotification into the channel's error context
  (`hObjectError`). The control has flags 0x8, so CPU-RM runs it and it is
  not routed to GSP.
- `kchannelConstruct` sets `notifyIndex[ERROR] = 0` and
  `notifyIndex[WORK_SUBMIT_TOKEN] = 1` (:506). Clients move the token slot
  with `NVC36F_CTRL_CMD_GPFIFO_SET_WORK_SUBMIT_TOKEN_NOTIF_INDEX` (0xc36f010a),
  which refuses index 0 (:4117). nvidia-push sets it to
  `NV_CHANNELGPFIFO_NOTIFICATION_TYPE__SIZE_1` (3) in `RequestChidToken`
  (`src/common/unix/nvidia-push/src/nvidia-push-init.c:303`). UVM
  (`nv_gpu_ops.c:5311`) leaves it at 1 and reads the token at
  `errorNotifier[1].info32`.
- A real RC error goes to slot 0. `krcErrorSetNotifier` → `krcErrorWriteNotifier`
  with notifierStatus 0xffff (`kernel_rc_notification.c:334`), or GSP-RM
  writes it through `errorNotifierMem` (set up in `kernel_channel.c:555`).
  Contents: info32 = the ROBUST_CHANNEL_* code (nverror.h), info16 = the NV2080
  engine type, status = 0xffff, status written last. RM clients test only the
  status: UVM `uvm_channel_get_status` (`uvm_channel.c:2046`) checks
  `status != 0`, and nvidia-push `nvPushCheckChannelError` checks `== 0xffff`.
- Our watchdog (`uapi.rs`) counted slot 0 as an error when **any** of
  status, info32 or the timestamp was nonzero. The token notification
  therefore killed every channel that lived through one watchdog poll
  (250 ms when idle). Channel 1 of each open (freed after about 106 ms) was
  lucky. The watchdog does not poll lazily: channel 2 was created at
  +27561 ms, channel 3 at +27693 ms, and the poll at +27800 ms caught both.
  That this came right after the EXEC was a coincidence.
- Open question for the next run: RM's code says the token notification
  goes to slot 1 with status 0xffff. The log read info32 = token with
  status 0 *through slot 0*. Both cannot be true unless our view of the page
  or RM's write differs from the source. The fix holds either way, and the
  next run logs where the token actually landed (section 4).

## 3. The fix (`drivers/nvidia/src/uapi.rs`)

1. CHANNEL_ALLOC calls `SET_WORK_SUBMIT_TOKEN_NOTIF_INDEX(3)` before
   `GET_WORK_SUBMIT_TOKEN`, as nvidia-push does. If RM refuses, this is
   logged and RM's slot 1 stays. The notifier page is 4 KiB (256 slots).
2. After the token, `check_token_notification` reads slots 0..3. It puts the
   slot that holds the token into the CHANNEL_ALLOC line
   (`token 0x4 (notifier slot 3)`). If the token is in slot 0 anyway, it
   logs a WARNING and clears slot 0; no work has run yet, so slot 0 cannot
   hold a real error at that point.
3. Watchdog: an error means **slot 0 status != 0**, as in UVM. As a second
   guard, a slot-0 entry that looks like the token (info32 == token,
   info16 == 0; a real RC error always has an engine type) is cleared with a
   WARNING, not treated as an error. The kill line now prints info32 in
   decimal with its nverror.h name and info16 as `engine`. The `rc_name`
   table was corrected against nverror.h: 68 is NVDEC0, 69 is
   GR_CLASS_ERROR, 8 and 109 are not in the header. CE errors, 44, 119 and
   120 were added.
4. The selftest client (`selftest.rs`) passes no `hObjectError`.
   `pErrContextMemDesc` is then NULL and RM writes nothing
   (`kchannelUpdateNotifierMem` returns early). It is unaffected.
5. ABI table (Rust `params.rs` and C `lnv_rmapi.c`): added
   SET_WORK_SUBMIT_TOKEN_NOTIF_INDEX and its params size, the
   WORK_SUBMIT_TOKEN and __SIZE_1 constants, and offsetof NvNotification.info16.
   `selftest=abi` in QEMU: **215** entries match, 0 mismatches.

## 4. On-screen milestones

`nvlog!` goes UART + klog only: the stick log has it, the monitor does not.

- New `crate::log_screen` / `nvscreen!` (`drivers/nvidia/src/lib.rs`)
  formats the **whole line** and hands it to the kernel's
  `serial_print_str_raw`. That is the same console sink nvprobe uses:
  UART + klog + framebuffer (VT 1), staged line-atomically. Each such line
  goes to exactly one sink, so a split line like the "phantom digits" bug
  cannot happen, and nothing is duplicated in the stick log.
- These lines go to the screen: `==== nouveau UAPI ready ...`,
  `==== nouveau UAPI NOT available ...`, `RM error notifier fired`,
  `HUNG ...` and `RM reported N new Xid line(s)` (`uerr_screen!`). Ioctl
  logs stay UART-only.
- Userspace: init's fd 1/2 are the raw console. The kernel's fast path sends
  them to `console_write_user` → `serial_write_byte_patient` →
  `console_mirror_byte`, which reaches VT 1's text plane and the framebuffer
  while VT 1 is on screen. nvk-autotest and nvktest output therefore
  already reaches the monitor. A QEMU screendump of the stick boot shows the
  whole nvk-autotest/nvktest block on the framebuffer. nvktest now also
  prints a `---- nvktest summary ----` recap of every result line just
  before `==== nvktest done`, also from its watchdog and crash handlers, so
  all results are on the last screenful instead of scrolled away among
  [INFO] lines.
- `nvidia-test-stick.sh` rebuilds nvktest when `nvktest.c` or
  `nvktest_spv.h` is newer than the binary. Before, it rebuilt only when
  the binary was missing, which would have shipped a stale nvktest.

## 5. The `ioctl nr 0x43 -> -2` lines (open 1, +15.7 s)

0x43 = DRM_COMMAND_BASE + 0x03. For nouveau that is CHANNEL_FREE. The caller
is `/bin/gpuprobe caps` (`ports/mesa/gpuprobe.c`, run by
`ports/greetd/data/gpu-env` when the greeter starts). It sends
`DRM_IOCTL_VIRTGPU_GETPARAM` (0xC0106443) twice, without first checking that
VERSION said `virtio_gpu`. Linux would route the same nr to
`nouveau_abi16_ioctl_channel_free` with channel id 7 (the param) and answer
-ENOENT. We answer ENOENT too, because that open has no channels and no
UAPI state. This is correct and harmless: gpuprobe reads it as "no
capsets", and the greeter prints the NO GPU RENDERER banner, which is right
on the PC. A gpuprobe that skipped the virtio ioctls on a non-virtio driver
would be tidier, but it is not needed.

## 7. Risks for fill / compute / triangle, from reading the path

- The EXEC path looks right against Linux gv100_fence_emit. One GPFIFO entry
  per push (SYNC_WAIT on NO_PREFETCH), then the kernel segment: SEM_ADDR_LO/
  HI/PAYLOAD_LO/HI/EXECUTE (5 contiguous methods, RELEASE + WFI + 64-bit),
  MEM_OP_A..D SYS_MEMBAR, NON_STALL_INTERRUPT, then GP_PUT in USERD and the
  doorbell token. ISR #3 fired 8 ms after the only EXEC, which suggests the
  GPU fetched the queue-init push and reached the non-stall interrupt. The
  semaphore value was not logged.
- Cross-channel waits: NVK's upload queue is channel 2 (copy class only).
  The main queue's EXECs wait on its timeline points, which
  `resolve_in_fences` waits for on the CPU (bound: `nvrm.uapi_timeout`, 10 s).
  If upload work never signals, fill shows `ETIME` after 10 s, not a hang.
- Wakeup: waiters wake on the RM ISR (`irq_hint`), a 1 ms re-probe and the
  100 Hz DRM tick. A missing non-stall interrupt costs latency, not
  correctness.
- RM's internal VA allocations (GR context buffers when c797/c7c0 are
  created) come from the same FERMI_VASPACE_A. NVK allocates top-down from
  2^38. A collision would show as a logged `VA range ... NV_ERR_*` on a
  VM_BIND, not as silent corruption.
- Copy class on a graphics channel: RM accepted c7b5 on the GR runlist
  (GRCE). The first fill is its first use from NVK.
- If something really faults, the next run reports it correctly as
  `RM error notifier fired: info32 31 = FIFO_ERROR_MMU_ERR_FLT, engine 0x..`,
  on screen and in the log, together with RM's Xid lines.
