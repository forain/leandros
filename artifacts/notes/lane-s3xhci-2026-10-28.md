# lane s3xhci (2026-10-28)

xHCI across S3 so the USB root stick survives a resume. Everything is behind `pm.s3=1` (the hooks are only called with the `PM_S3` flag); the default path is unchanged.

## What
- `drivers/usb/src/xhci/pm.rs` (new). Suspend (Linux `xhci_suspend`): wake bits cleared, enabled ports to U3 (PLS=3 with LWS), `R/S=0` and HCH, op + interrupter-0 registers saved
  (CRCR is kept as our own ring position), then `CSS` and wait `SSS=0`.
  Resume: `restore_state()` first (DCBAAP must still read back, `CRS`, `RSS=0`, no `SRE`, `R/S`, ports U3 -> U0 with LWS, a NO-OP command must complete),
  otherwise `reinit()`: HCRST on the SAME controller object, zeroed DCBAA (scratchpad array kept, pages zeroed), rings reset, interrupter and CRCR re-programmed,
  ports powered; then USB persist.
- USB persist is done IN PLACE under the old slot id: Enable Slot until the old ids are back (extras disabled), port reset, Address Device, GET_DESCRIPTOR(device) and
  the serial string compared with the copy saved at enumeration, Configure Endpoint with fresh rings, SET_CONFIGURATION (+ SET_INTERFACE). The class-driver transport
  (`XhciBulk`: slot + endpoint numbers) stays valid, so the blkdev, the f2fs mount and the root do not move. Only bulk-only mass-storage devices on a root port carry a
  `Persist` record. Hubs (and everything behind them), HID, audio, video are marked gone; the hot-plug scan re-enumerates them from the connect-change latch (not proven on hardware).
- `usb_storage::pm_resume_check()`: `ScsiDisk::init()` again (TEST UNIT READY with UNIT ATTENTION retry, INQUIRY, READ CAPACITY) and the capacity must equal the
  saved one. A mismatch marks the disk gone (no further I/O, no writes) and fails the resume hook with `[S3] root/usb device changed across suspend ... no writes`.
- The hot-plug scan is suppressed from suspend until the controllers are back (`PM_ACTIVE`).
- Knob `pm.s3_xhci=auto|restore|reinit` (auto = restore, else reinit).
- Wiring: `kernel/src/pm.rs` xhci hooks call `usb_hcd::pm_suspend_s3/pm_resume_s3` when `PM_S3` is set; the older `pm_suspend/pm_resume` (pm_test=devices etc.) are untouched.

## Evidence (QEMU x86_64 TCG, `--usb-stick` GPT image built with `LEANDROS_USB_EXTRA_CMDLINE="pm.s3=1 nosmp"`, root on qemu-xhci)
- Real S3 with `echo +8 > wakealarm; echo mem > state`: `RESUMED from S3; PM1_STS 0x8401 (RTC 1 WAK 1)`, `[XHCI] bus 1: state lost, reinit`,
  `resume xhci: ok in 363 ms: bus 1 reinit: 1 device(s) re-addressed in place, 0 lost; 1 usb disk(s) same capacity`, `resume block: gate open`,
  a file written before the sleep reads back, a write after the resume is synced and readable (S3_RC=0).
- `pm_test=core` (`echo core > /sys/power/pm_test`) on the stick: `CORE_RC=0`, xhci suspended/resumed in place.
- 3 fresh boots, each: `pm_test=core` then one real S3 (+6 s alarm): 3/3 resumed, xhci reinit in place (core 107 ms, real 358 ms), `1 usb disk(s) same capacity`, a write after the resume synced and readable.
- The restore path (CSS/CRS) is NOT exercised by QEMU: its xHCI does not implement Save/Restore State, so the attempt ends in `restore failed (DCBAAP lost)` (real S3: QEMU reset the controller) or `(SRE after restore)` (pm_test=core), and the fallback reinit runs. The restore path is therefore unproven; `pm.s3_xhci=reinit` skips it, `restore` forbids the fallback.
- Hang hardening (orchestrator note, power LED solid + button dead = awake and hung): every poll in suspend/resume is bounded (port U3 10 ms, halt 16 ms, CSS 20 ms, HCRST 1 s, commands 2 s each) and each step logs `[XHCI] bus N: S3 suspend: ...` before and after.
- Known QEMU limit (pre-existing, not xHCI): a SECOND real S3 in the same boot hangs (without a USB stick it hangs in virtio-blk, `device_status 0x00`, because QEMU resets the virtio devices at the wake; with the stick the second `entering sleep now` never returns). Test one S3 per boot (`--repeat`).

## Not done / open
- Devices with interrupt or isochronous endpoints (HID, hubs, audio, UVC, Bluetooth) are not persisted; they depend on the connect-change latch for re-enumeration after a reinit (unproven on hardware).
- SPT-LP PME quirk (8086:9d2f, vendor reg 0x80A4 bit 28) is phase 2 (wake only).
- No UAS devices. Root stick behind a hub is not persisted (marked gone: the root would be lost).
- `pm.s3_xhci_flush` of klog before the block gate is s3core2's job.

## Real S3 on the laptop: attended test plan (user at the laptop, never unattended)
Precondition: main with s3core2 + this lane, laptop trial built with INTEL=1, cmdline = the good entry's plus `pm.s3=1 nosmp pm.s3_beep=1 pm.s3_reset_after=90` (use remote.py, never a bare `espctl cmdline`).
1. Boot the trial, ssh in, `echo core > /sys/power/pm_test; echo mem > /sys/power/state` (no AML, no power loss): expect `[PM] suspend xhci: ok ... 1 port(s) in U3`, `[XHCI] ... restore failed (...) , reinit` or `restored`, `resume xhci: ok ... re-addressed in place, 0 lost; 1 usb disk(s) same capacity`, ssh still works, `touch /root/x; sync` ok. Repeat 3x.
2. Check klog (`dmesg | grep XHCI`) for the step lines; if the step lines stop at `halting`, the hang is the halt; at `saving state`, CSS.
3. User present: `echo +20 > /sys/class/rtc/rtc0/wakealarm; echo mem > /sys/power/state` over ssh in the foreground. Watch: power LED pulses (S3), after ~20 s the machine wakes (beep). If nothing after 2 min: hold power 4 s. If the LED stays solid the whole time the sleep never started (hang in devs_suspend, check the last `[XHCI]`/`[PM] suspend` line in klog after the next boot).
4. After wake: ssh back within ~30 s, `dmesg | grep -E "S3|XHCI|resume"`, file write on the root stick, USB keyboard/mouse (will re-enumerate via the latch or stay dead: record which).
5. Compare `pm.s3_xhci=reinit` (default path on power loss) with `pm.s3_xhci=restore` once to learn whether the PCH keeps the xHC state.
