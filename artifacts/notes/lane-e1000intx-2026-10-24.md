# lane/e1000intx 2026-10-24 — e1000e RX on INTx when MSI is unavailable (L9.10)

## FIXED: RX (and so the whole data path) is interrupt-driven on INTx
- `drivers/src/e1000e.rs`: the INTx fallback (aarch64, no GIC ITS) no longer strips `IRQ_EN_RX` /
  `RX_IRQ`; it arms the same causes as the MSI path (`e1000e.rxirq=0` still keeps RX polled).
  The level handling was already correct: ISR reads ICR (read-to-clear without MSI-X), writes IMC
  (QEMU drops the line), returns, then EOI; the daemon's IMS write re-raises the line if a cause
  latched meanwhile. No ISR change was needed.
- The 0.03 Mbit/s crawl seen by lane linkmon did NOT reproduce (5 bulk uploads, 2 downloads, all at
  line rate). Its cause was not found; treat it as REFUTED for the current tree.

## ITS (goal 2) — findings, not implemented
- `-accel hvf -M virt,gic-version=3,its=on` -> "ITS not supported on HVF when using the hardware
  vGIC" (QEMU 11.1 uses the macOS in-kernel vGIC; it also refuses GICv2).
- `-accel hvf,kernel-irqchip=off` brings back QEMU's userspace GICv3 and `arm-gicv3-its` works
  (info qtree shows the ITS). TCG has it too. Cost: userspace GIC emulation on every IRQ/EOI.
- Our kernel has no ITS driver (`arch/aarch64/src/gic.rs`, `drivers/src/irq.rs` `request_msi`
  -> Unsupported). An ITS driver (LPI prop/pending tables, device/collection tables, command
  queue MAPD/MAPC/MAPTI/INV/SYNC) would give MSI on TCG and on HVF with kernel-irqchip=off, and on
  real GICv3 boards (Pi5 has GICv2 + no ITS, so not there). Not needed for e1000e now.
