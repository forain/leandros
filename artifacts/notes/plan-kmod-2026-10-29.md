# Kernel modules Y/M/N — synthesized plan (2026-10-29)

Inputs: design-kmodA-2026-10-29.md (faithful Linux), design-kmodB-2026-10-29.md (pragmatic). Read both; this file says which parts win.

## Stage 1 — Y/N (take kmodB)
- Vendored kconfiglib + `scripts/menuconfig.sh`; Kconfig tree; `.config` → cargo features + module list (kmodB L0).
- Per-driver feature with a same-API stub when off: no call-site churn, init order unchanged (kmodB). No initcall registry in stage 1.
- defconfigs per target (x86_64 qemu, x86_64 laptop INTEL=1, aarch64 qemu, rpi5) = all Y.
- MERGE GATE: all-Y kernel byte-identical (or disassembly-identical if builds are not reproducible) to the previous main, on x86_64, aarch64 and rpi5.
- Lanes: L0 plumbing → L1a net ∥ L1b gpu ∥ L1c misc → L2 size/boot measurement.

## Stage 2 — M (kmodB mechanism + kmodA guards)
- Mechanism (kmodB): modules fully linked at build time to a fixed slot in a reserved KVA window (no KASLR → no relocation engine), with a build-id lock. They ship in the initrd under lib/modules/<build-id>/, so kernel and modules always travel together (both designs agree).
- Boundary (both agree): modules may call ONLY an explicit exported `kapi_*` extern "C" list. These are #[no_mangle] and kept through LTO.
- Guards adopted from kmodA:
  - A link check: a module's undefined symbols must all be kapi_* (no kernel crate linked twice, no second copy of kernel globals).
  - A softfloat/no-SIMD instruction scan of every aarch64 module (the FP/SIMD clobber lesson).
  - The vendor/spin lock-tracking hook reports through kapi.
  - An owner tag on every registration (prepares for unload later).
  - W^X mapping, plus aarch64 I-cache maintenance before running module code.
- No unload in v1 (kmodB). Autoload by a generated id table (pci/usb/dt/acpi); `modules.load=`, `modules.blacklist=`, `kmod=0` on the cmdline. On failure the device stays unbound and boot continues.
- Deferred from kmodA (later, if needed): per-symbol CRC modversions, the PIC .so format, rmmod/unload, and splitting drivers into separate `modules/<name>` crates on top of the kapi crate.
- First modules: virtio_rng → e1000e (QEMU + laptop) → uvc. Boot-path drivers and i915 stay Y.
- Lanes: L3 kernel side (exports, loader, syscalls, build-id) → L4 module build pipeline → L5 virtio_rng → L6 e1000e → L7 uvc → L8 Pi check.
- Open checks for L3: the module window is unmapped on every layout including rpi5; `--build-id` added to the kernel link; a netdev registered after boot is seen by netd/netwatch.
