# lane/x86tlb — 2026-10-20 (L1.14: x86_64 syscalltest `uaccess_fs` 4/4)

## Verdict: premise REFUTED — no stale TLB entry; a partial store by pipe2

The kernel was not reading through a stale translation. It read bytes that an
earlier syscall in the same loop iteration had written:

1. `ua_fs` loops over the bad pointers; for the straddle pointer (`m+pg-2`,
   2 mapped bytes 'a', then an unmapped page) it calls getdents64, getcwd,
   **pipe2**, then memfd_create / getxattr name / mount target.
2. pipe2 stores its `int fds[2]` with `write_user`. On x86_64 the uaccess copy
   is `rep movsb`, byte by byte: it stores the low two bytes of `fds[0]`
   (`0x04 0x00`, fd 4) into the mapped head, then faults on the tail page.
   pipe2 correctly returns EFAULT, but the head now holds `"\x04\0"`.
3. memfd_create etc. then read a valid NUL-terminated 1-byte name `"\x04"`
   and succeed. That is the 0x04 the temporary print showed.

aarch64 passes because its copy loop moves 8 bytes with one `ldr/str x`, and
that store faults as a whole before it writes anything.

The make_bad user-mode checks ran before the loop, so they saw 'a'.
vmreuse2, PCID and shootdowns are not involved.

## Fix
- `sched/src/uaccess.rs` `write_user<T>`: all or nothing, like Linux
  `put_user`. A `T` that crosses a page boundary is stored tail page first,
  so a fault on the tail leaves the head untouched. Covers all 21 callers
  (pipe2 fds, FIONREAD ints, ...).
- `userland/syscalltest/syscalltest.c` `ua_fs`:
  - pipe2 on the straddle must leave the head "aa". This check FAILS before
    the kernel fix on x86_64.
  - Before each string-reading case, refill the straddle head. Output
    syscalls such as getcwd legally leave a partial store (Linux too).

## Test evidence
- x86_64 (TCG) regress: all RC=0, including syscalltest (fails=0).
- aarch64 (HVF) regress: syscalltest fails=0. pollnarrowtest, nettag2test and
  kparkstest failed only under host load (the x86 TCG run in parallel). All 3
  re-run RC=0 under the qemu lock.
- The pipe2 "head untouched" check was not run against the old kernel. The
  integration run's 0x04 (fd 4's low byte) shows the failure it guards.
