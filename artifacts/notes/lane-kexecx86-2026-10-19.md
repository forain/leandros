# lane/kexecx86 (2026-10-19)

x86_64 half of lane 3 (`artifacts/notes/kexec/PLAN.md`): `reboot(KEXEC)` boots
the `kernel-direct` image staged by `kexec_file_load`, through multiboot2.

## Changes
- **kernel-direct linked at 32 MiB** (`linkers/x86_64-direct.ld`, `. = 0x2000000`):
  OVMF keeps ACPI NVS at 0x800000-0x900000 and firmware ranges up to
  0x1780000 (the HP has a hole at 0xC00000-0x1022000), so the old 1 MiB
  destination was always refused (EADDRNOTAVAIL). The image now covers
  0x2000000-0x396a000; the initrd stays at 0x10000000, the trampoline's
  0-2 GiB map covers both. MB1/MB2 headers sit at file offset 0x1000.
  `main.rs` reserves the image from `direct_image_base()` (`_start_pvh` page).
- `kexec/exec_x86_64.rs` + `purgatory_x86_64.s` (mirrors aarch64):
  `prepare` builds a purgatory page below 4 GiB and an identity map (2 MiB
  pages over every GiB holding RAM; PML5 root under LA57) outside every
  destination. `stop_and_jump`: on an AP, arm `idt::NMI_DIVERT` and NMI the
  BSP (INIT to the BSP would restart the firmware); the BSP INITs every
  other started CPU (wait-for-SIPI), masks every IOAPIC RTE
  (`ioapic::mask_all`), LAPIC LVTs/timer/TSC deadline, EOIs in-service
  vectors, masks the 8259 (`apic::kexec_quiesce`), copies the live upper
  half into the identity root, loads it and jumps. Purgatory: own GDT, null
  IDT, indirection-list copy, PCIDE/PGE off, `retfq` to 32-bit compat, PG
  off, EFER.LME off, CR4 = PAE, CR3 = 0, EAX=0x36d76289, EBX=MBI, `jmp`.
- `power.rs`: `kernel_kexec` and `quiesce_all_pci` no longer aarch64-only.
- `entry_x86_64.s` `.Ltarget`: `mov ebx, esi` (upper halves undefined).
- MBI builder (`boot/src/mb2_build.rs`): below 1 MiB the loader's types now
  pass through (only page 0 forced Reserved). Forcing the whole MiB Reserved
  left the kexec'd kernel on 1 CPU (`[SMP] trampoline page 0x7000 is not
  usable RAM`) and gave a chained load no low page for its own MBI. The
  buddy never allocates below 1 MiB, so nothing else changes.
- Chained load on a direct boot: the running image and initrd are Reserved
  in its MBI map but are exactly the destinations; `info::with_own_image`
  adds them to the loadable spans. The MBI we booted with stays live
  (`rsdp_addr` points into it): `BOOT_MBI_RANGE` keeps the next MBI off it
  (gen 2's MBI went to 0x29000).

## Test (TCG, OVMF/Limine, 4 CPUs, 4 GiB, plain virtio-gpu)
`kexectest` ALL PASS (load now succeeds on x86), then `kexectest -e` twice:
- gen 1: `[KEXEC] exec plan: purgatory=0x7ce89000 (560 B) idmap ... (4 GiB, 4-level)`,
  `PCI quiesced: 9 virtio device(s) reset ... 11 function(s)`,
  `BSP: INIT sent to 3 CPU(s)`, then `PGp3EMJ6![early] boot protocol
  0x36D76289 info 0x28000`, `[early] cmdline: kexec.gen=1`,
  `[SMP] 4 CPUs online`, login as root, `/proc/cmdline` = `kexec.gen=1`, `nproc` 4.
- gen 2 (chained, from the kexec'd kernel): MBI 0x29000, same sequence,
  `kexec.gen=2`, 4 CPUs, login.
- `--direct` (QEMU multiboot1) still boots the new base (`boot protocol
  0x2BADB002`); it then mounts vdb as root and login fails, because a
  direct boot has no root=/boot-disk identity (unrelated to this lane).
- Host tests: `boot/bootparse-tests` 11/11 (low-memory expectations updated).
- aarch64 sanity (HVF, Limine, plain virtio-gpu): 4 CPUs, login, `kexectest`
  ALL PASS, `kexectest -e` (called on cpu1, cpu0 took over) -> gen 1 login
  with `kexec.gen=1`; 1 CPU there is the known HVF CPU_ON issue (lane kexecexec).

## Open
- The AP-caller path (NMI hand-off to the BSP) is not exercised: both runs
  had reboot(2) on cpu0. No thread affinity to force it.
- Not tried under KVM or on the laptop; no device reset beyond virtio +
  BME/MSI (real NICs/GPUs untouched), RAM above 2 GiB is still Reserved for
  the direct kernel.
