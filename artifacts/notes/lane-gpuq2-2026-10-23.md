# lane/gpuq2 (L11.5) - follow-ups of lane/gpuq

FIXED.
1. RING_IDX on virgl: execbuffer now refuses (EINVAL) RING_IDX for ANY ring, including ring 0, on capset 1/2
   (was: only ring != 0). Mesa virgl never sets the flag; a ring-0 fence on a context closed mid-flight hung
   QEMU's vrend like ring>0. Guard: gpuqtest VIRGL_RING0_EINVAL (ctx_init virgl NUM_RINGS=1, ring 0).
   Failed on the unfixed driver (aarch64 --virgl), passes after; gpuqtest + drmsmoke green with --virgl.
2. Bounded ctrlq wait: new CTRLQ_WAIT_MAX_US = 2 s wall-clock checked in CtrlqWait::step (spin and park paths),
   park deadline 5 s -> 2 s. A timed-out synchronous submit marks the device dead for 3 s
   (CTRLQ_DEAD_UNTIL_US); submit_begin then fails immediately (Err -> EIO to callers) so other CPUs queueing on
   the lock do not each burn another full bound; the next submit after the window probes. Previously the bound
   was 100M iterations (minutes). The ioctl path (GpuLocked::submit) already waits with the lock released;
   the locked path (init/console/cursor) is what could wedge CPUs.
   No forced-timeout knob (would need a new debug interface); reasoning only.

Accepted, not changing: fence IRQ BSP-only (by design); Venus untested on the Mac (host limitation).
Regress aarch64: all green except pollnarrowtest (known flake, passes alone on rerun).
