# lane/irq23 — 2026-10-23 — FIXED (L5.13)

## Root cause
On QEMU virt aarch64, virtio-gpu (slot 4, INTA) and virtio-net both land on
INTID 0x23 (SPI 3); virtio-input arms INTx on the PCIe SPIs too. The GPU
registered its INTx handler in the arch GIC table (`arch_request_irq`), net and
input in the `drivers::irq` line table. `handle_irq` calls both tables, but the
line table's storm guard only sees its own sharers' verdicts: every GPU
completion counted as "unclaimed" for net/input, so 1000 GPU interrupts with no
net RX in between masked the line ("[IRQ] line 0x00000023 fired 1000 times with
no handler claiming it; masked"). That starved net/input INTx and the GPU's own
completion interrupt (CTRLQ_IRQ_ARMED stayed true, waiters parked on an
interrupt that no longer came). The GPU's private guard had the mirror bug
(1024 net-only deliveries would mask the line for everyone).

Evidence: 37 of 159 past runtests runs with net INTx armed (/tmp/ffsession)
show the line, e.g. tests-eu-reg; lane-f2fsrecov2-2026-10-23.md shows it in
f2fsfulltest seed 5 on main 079f074a.

## Fix
- virtio-gpu INTx is a `drivers::irq` line sharer (`request_irq(Line)`,
  returns Handled/None); its private storm guard is gone. One dispatcher,
  one guard over all sharers.
- Line table: per-sharer claim counts, `masked` state + `irq::line_masked()`
  (virtio_gpu::irq_armed() refuses to park on a masked line); the storm
  message now lists each sharer's handler address and claim count.
- virtio-input reads its ISR byte with `mmio_read` (HVF-safe accessor).
- runtests.py: a run whose kernel log contains a storm-guard mask FAILS
  (regex verified against tests-eu-reg's log).

## Verification (aarch64, HVF)
- f2fsfulltest --iters 5 --seed 5: PASS, 0 "fired 1000" lines.
- full regress (tests-irq23reg): 0 storm lines; GPU/NET/INPUT INTx armed on 0x23.
  Network suites red (nettest, udptest, netctltest, sshsmoke, listentagtest,
  vfstagtest) from a SEPARATE bug: "[NET] eth0: address 10.0.2.15/24 removed
  (lease lost)" printed right at scheduler start, ~1 s after "stack up";
  no IRQ storm in that run. Reported to the orchestrator as a new item.
