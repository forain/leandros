# lane/ccfs: Claude Code CLI could not run commands or write files (2026-10-14/15)

Branch `lane/ccfs` off main 9f4f1753. Pushed to origin as `lane/ccfs` only (not main).

## Symptoms (user report)
As leandro through `/bin/claude` (2.1.296):
1. The Bash tool and the `!` prefix failed with "task output swap refused (tasks dir moved or linked)".
2. Every new file failed with "Error: ENOENT: no such file or directory, open '<path>'".

## How the CLI writes (from the JS embedded in the Bun binary)
`pinWriteTarget` (minified `Xr`/`Ub`) does this on Linux for every write target, including the
task output file `/tmp/claude-<uid>/<project>/<session>/tasks/<id>.output`:
1. It opens the nearest existing parent with `O_PATH|O_DIRECTORY|O_CLOEXEC`.
2. It reads `/proc/self/fd/N` and requires the result plus the missing components to equal the
   path it was asked to write.
3. For each missing component it calls `mkdir("/proc/self/fd/N/<c>")` and reopens it with
   `open("/proc/self/fd/N/<c>", O_PATH|O_DIRECTORY|O_NOFOLLOW)`. Then it reads the link again.
4. It writes, creates or unlinks through `/proc/self/fd/N/<leaf>`.
5. The task-output cache keeps the directory fd. Before reusing it, the CLI checks that
   `fstat(fd)` and `lstat(dir)` give the same `st_dev`/`st_ino`. Output is read back through
   `/proc/<own pid>/fd/M`.

An ENOENT from the mkdir in step 3 is taken as "held directory vanished". The CLI retries three
times and then throws `SymlinkWriteRefusedError`. The task-output code reports that as "tasks dir
moved or linked". An ENOENT from the open in step 4 is the Write tool's error.

## Root causes and fixes
1. **Kernel: nothing below `/proc/self/fd/N` resolved.** The VFS treats `/proc/self/fd/N` only as
   a leaf, the reopen-by-identity case. `kernel/src/syscall.rs`:
   - `proc_own_fd` parses `/proc/<self|thread-self|own pid>/fd/N[/rest]`.
   - `proc_fd_below` maps `/proc/<own>/fd/N/<rest>` to the fd's backing path plus `<rest>`. It is
     applied first in `KPath::from_ns`, after the alias translation, so it also works in a chroot
     where `/proc` is an alias mount. It is also applied in `backing_of`.
   - The namespace form of such a path is the directory's real location, mapped back through
     `alias::reverse`, so `chdir` below it records a stable cwd.
   - `chdir("/proc/self/fd/N")` is `fchdir(N)`.
   - `open("/proc/<own numeric pid>/fd/N")` of a non-mounted file is passed on as
     `/proc/self/fd/N`, the only spelling the VFS reopens by identity.
2. **VFS: tmpfs directory inode numbers disagreed.** `stat` reported an FNV hash of the path, while
   `fstat` reported `0x2000_0000 + slot`. So the CLI's cached pin of its tasks directory always
   looked swapped. `stat_common` now reports the slot inode as well.
3. **VFS: root got ENOENT for `/tmp/file/x`, not ENOTDIR.** `tmp_check_traversal` returned early
   for euid 0. It now walks for everyone and skips only the permission check for root. The test
   exposed this one. The CLI did not depend on it.

## Tests
- chroottest `procfd_walk` (f2fs, /var/tmp), `procfd_walk_tmpfs` (/tmp) and
  `procfd_walk_chroot`. The last runs in a chroot with `/proc` mounted and `/tmp` bind-mounted,
  as uid 1000, which is the CLI's setup. The cases run the sequence above and check:
  - readlink after each step;
  - fstat against lstat on the held directory and on the file;
  - rewrite, unlink and rmdir through the magic path;
  - a `/proc/<pid>/fd/N` reopen;
  - ENOTDIR below a file fd and ENOENT below a closed fd;
  - `chdir` to the link and below it, then `getcwd`.

  chroottest is already in `--suite regress`. Before the VFS fixes, aarch64 failed with
  `fstat(held) 1:20000006 vs lstat 1:986babd11b3f` and then with ENOENT where ENOTDIR was
  expected. The kernel-only failure (ENOENT on the mkdir) was not re-run on an unfixed image.
  The previous attempt's uncommitted diff was this same fix, half done.
- `scripts/ccfs-mock-api.py PORT` is a scripted Messages API (SSE). It sends Bash, then Write to
  a file in two new directories, then Bash `cat`, then end_turn.
  - Guest command: `ANTHROPIC_BASE_URL=http://192.168.105.1:PORT ANTHROPIC_API_KEY=x claude -p go
    --dangerously-skip-permissions`. 192.168.105.1 is the host under socket_vmnet; with SLIRP use

## Open
- `/run/user/<uid>` is not mounted into the Alpine root, so the CLI's cross-session messaging is
  off ("Failed to set up sockets directory"). Only a debug-log error.
- Paths below `/proc/self/fd/N` use the fd's open-time path, because the VFS has no dentries.
  A renamed directory is not followed. readlink of a removed directory's fd has no " (deleted)"
  suffix; the CLI uses that suffix only to retry sooner.
- The new cases were not run on a Linux host, because the boxes were unreachable.
- The TUI `!` prefix was not driven directly. It uses the same task-output pin as the Bash tool.
