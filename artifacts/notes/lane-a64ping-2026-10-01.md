# Lane a64ping — 2026-10-02

Branch `lane/a64ping` @ `c62c940` (base origin/main `f0c8994`). Machines: Mac (aarch64 HVF, plus one x86_64 TCG A/B run) and desktop (x86_64 KVM).

## Outcome: premise REFUTED (not aarch64); two real bugs fixed

The integ1003/privcheck symptom "aarch64 `ping 10.0.2.2` prints the header and hangs" has two separate causes. Neither is aarch64-specific.

1. **10.0.2.2 does not exist on the Mac.** The Mac runs the `socket_vmnet` daemon (pid 429, root, `--vmnet-gateway=192.168.105.1`). Because of that, driver.py and run-qemu.sh wrap QEMU in `socket_vmnet_client` with `-netdev socket,fd=3`. The guest then gets 192.168.105.x by DHCP, and its gateway is 192.168.105.1. A ping to 10.0.2.2 leaves through the Mac's default route and nothing ever answers it. On the desktop (Linux) the backend is SLIRP, which is why x86_64 got 4/4.
   - Old image, aarch64 HVF vmnet: `ping 192.168.105.1` 4/4 (12–23 ms); `ping 10.0.2.2` hangs.
   - Old image, aarch64 HVF with SLIRP forced: `ping 10.0.2.2` 4/4.
   - Old image, **x86_64 TCG on the Mac (vmnet)**: `ping 10.0.2.2` also hangs (still alive after 25 s), and `ping 192.168.105.1` gets 4/4. So the arch does not matter; the host backend does.
   - The filter-dump pcap of a SLIRP boot shows the full DHCP exchange (offer/ack, DNS 10.0.2.3).
2. **ping never timed out** (fixed, `a5c9f3a`). ping assumed recvfrom on its ICMP socket was nonblocking. The kernel's `net_blocking_op` parks a blocking recvfrom until data arrives, so with no reply, ping slept in recvfrom forever and never printed "Request timeout". Fix: wait with `poll()` bounded by the per-packet timeout, then read with `MSG_DONTWAIT`. I also added `-c/-W/-i`, the reply's source address, and a `% packet loss` line, and sends are now paced from the previous send. SIGINT does end the blocked recv (ERESTARTSYS path checked), so the kernel side is fine.

Also: `LEANDROS_NET=user` (driver.py + run-qemu.sh, `c62c940`) forces SLIRP on a vmnet Mac.

## nettest (new suite, `/bin/nettest`, plain C like privtest)
`nettest [-g gw] [-d dns] [-n name] [-t ip:port]` covers these cases:
- icmp_raw and icmp_dgram: 4/4 echo replies required.
- icmp_nonblock: MSG_DONTWAIT gives EAGAIN at once.
- icmp_poll_timeout: 700 ms poll with no reply returns 0.
- icmp_recv_eintr: a blocking recvfrom is ended by SIGALRM with EINTR.
- udp_dns_raw.
- udp_getaddrinfo: musl resolver via /etc/resolv.conf.
- tcp_dns: the DNS query over TCP port 53.
- tcp_http: GET from a host `python3 -m http.server`.

I checked it on the hosts first. Mac: 7 PASS, 2 SKIP. Linux desktop as a user: 7/0/2. Linux under sudo: 8/0/1.
