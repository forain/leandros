# Lane pid0c: BCM2712 D0 overlay on the card, stepping from the chip id (2026-10-26)

Status: FIXED (card plus hardware stepping detection). Needs a real Pi boot to confirm the chip-id address and decoding.

## Evidence (real Pi 5 boot, $SP/piirq/boot.txt)
- The firmware read `bcm2712-rpi-5-b.dtb`, then looked up `/overlays/overlay_map.dtb` and `/overlays/bcm2712d0.dtbo`.
  The card has no overlays dir, so the live DT stayed C1 on a D0 chip (uart10 = SPI 120).
- `[sdio] FAIL stage=cmd5 ... pinmux=C0 sd2-fsel-before=569900 writes=11`: the C0 table was used on D0.
- Decoding of `569900` (packed nibbles for pins 30..35, read at the C0 slots) on D0 silicon:
  pin30/31 → mux reg 3 nibbles 6,7 = 0. D0 has no mux field there (D0 mux stops at reg 3 nibble 3 = gpio35).
  pin32..35 → "mux reg 4" nibbles 0..3 = 9,9,6,5. On D0, reg 4 is the first PAD register: bits[15:0] = 0x5699, which is
  pad slots 0..4 (reserved) plus gpio1..3 pull-down defaults. "9" is not even a valid fsel (FSEL_COUNT = 9).
  So the value says nothing about sdio2. The probe then made 11 writes to the wrong fields (pad reg 4 slots 0..7, C0 pad reg 9),
  and D0 gpio30..35 were never muxed to sd2. That accounts for the CMD5 timeout. The pads were reset again at the next power cycle.
- D0 rows rechecked against raspberrypi/linux rpi-6.12.y `pinctrl-bcm2712.c`: GPIO_REGS(28,2,4,5,10), (30,2,6,5,12),
  (31,2,7,5,13), (32,3,0,5,14), (33,3,1,6,0), (34,3,2,6,1), (35,3,3,6,2). sd2 is f1 on D0 pins 30..35, so fsel = 1
  (`bcm2712_pinctrl_fsel_set` uses a 1-based function index and fsel 0 = GPIO). gpio28 (WL_ON) uses fsel 0. Pulls: none on 30, up on 31..35.
  The existing D0_PINS table was already correct. Only the stepping choice was wrong.

## Changes (37815a2c)
- `scripts/prepare-rpi5-sdcard.sh` (direct): ships `overlays/overlay_map.dtb` (sha256 2d4617de...) and
  `overlays/bcm2712d0.dtbo` (sha256 b73210c9...) from raspberrypi/firmware 88a0ae88, sha256-checked. It drops
  `bcm2712d0-rpi-5-b.dtb`, which the firmware never reads (only an explicit `device_tree=` would load it), and removes
  that file from an old card.
- `drivers/src/bcm2712_id.rs` (new): reads SUN_TOP_CTRL CHIP_FAMILY_ID (+0) and PRODUCT_ID (+4) at 0x10_0150_4000.
  The block is inferred from the stock `reset-controller@1504318` (brcmstb-reset = SUN_TOP_CTRL + 0x318) plus the soc ranges.
  The revision is decoded as in Linux `brcmstb/common.c` (0x2x = C → C0 layout, 0x3x = D → D0). If the id is not a
  0x2712 C/D part, it falls back to the DT pinctrl compatible. It logs once:
  `[bcm2712] stepping=D0 (hw) chipid=<family>/<product> dt=<..>`.
- `sdio_host.rs` takes the pin-mux table, and `gic.rs` probe_uart_line takes its fallback (`hw=d0` / `dt=d0`), from it.
- sdio-tests 17/17 (4 new: chip-id decoding; hw beats DT, which is the real-board D0-chip/C1-tree case the old DT-only choice got wrong;
  pin rows vs Linux; C0 slots never alias D0 sd2 fields).
