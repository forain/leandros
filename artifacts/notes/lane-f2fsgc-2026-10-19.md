# lane f2fsgc — 2026-10-19 (bug list L4.1)

## L4.1 "no segment cleaner -> ENOSPC with blocks free" — FIXED (SSR, not a migrating cleaner)
Premise confirmed: `sit_find_free_seg` only returned segments with vblocks == 0, so once
deletes left every segment partly valid the allocator answered ENOSPC. Reproduced with
`f2fs.ssr=0` (old allocator): ENOSPC after 58 MiB written on a 62 MiB volume with live data
27 MiB and 28 MiB free.

Design choice: this server updates node and data blocks **in place** (overwrites never move a
block; NAT entries are rewritten unchanged), so nothing invalidates blocks behind the logs.
The only fragmentation comes from unlink/truncate. Upstream f2fs answers low free segments
with SSR (slack space recycling): a log that has no free segment takes the free blocks of a
dirty segment. Implemented exactly that (`log_alloc`, `ssr_pick`, greedy: the segment with
the most usable blocks). It reaches every free block, and no valid block is moved. A
migrating cleaner would buy nothing here. It would also need per-segment summaries to find
each block's owner, and the SSA area of these images covers only 512 segments (no
summaries are written).

Crash safety: this follows upstream's checkpoint-valid-map rule. A block freed since the
last durable checkpoint is never allocated (`prot_pending`/`prot_inflight`, per-segment
bitmaps), and a segment emptied by frees stays PRE_FREE until then. The snapshot is taken in
checkpoint phase 1, released when the commit block is on the medium, and merged back if the
checkpoint failed. A request that finds only such blocks is doomed like a cache miss, so its
page-cache write-through is skipped and it is undone. `with_mount` then runs a checkpoint
(`space` in `[ckpt]`) and retries. ENOSPC comes only after two checkpoints made no room.

## Found on the way (fixed)
- **Latent data loss in every populated root image.** `mkfs-f2fs-populated.py` (and
  `-minimal.py`) wrote SIT entry k for main segment k-7, plus 7 "metadata, full" entries. The
  server indexes by main segment, as upstream does, so the two runtime log segments started
  with vblocks 512 and an all-ones valid map. Each allocation then counted again, and after
  512 allocations with no free in that segment the 10-bit vblocks wrapped to 0. The segment
  then read as free while full of live inodes or data, and was reused. The current root
  image showed it: seg 896 vblocks 528 against 88 valid bits.
  Fixes: the builders index correctly, `sit_mark_block_used` counts only a newly set bit, and
  the mount repairs vblocks from the valid map (`sit_repair`). The valid map was always a
  superset of the blocks in use, so the repair is safe. Old images keep about 5 leaked
  segments (10 MiB), never lost data.
- **Node-id exhaustion overwrote the SSA and main area.** `next_free_nid` had no bound, and
  nids are never recycled. Now `take_nid` returns ENOSPC once the NAT is full.

## Open
- Torn checkpoint: NAT/SIT/node blocks are written in place during the flush. A power cut
  in the middle of a checkpoint is not atomic (pre-existing; no shadow NAT/SIT copies).
- Node ids are still not recycled; a long-lived volume eventually hits the NAT bound
  (465,920 ids on these images).
- Directory i_links: mkdir creates dirs with links 1 and never bumps the parent (fsck
  warnings only).
- No idle background cleaner; with SSR none is needed for space. Defragmentation for
  sequential write speed on the USB stick is not addressed.
