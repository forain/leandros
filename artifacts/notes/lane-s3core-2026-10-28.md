# lane s3core (2026-10-28)

PARTIAL: real S3 works in QEMU x86_64; the first real-laptop attempt did not come back (LAPTOP NEEDS POWER BUTTON).

## What
- `arch/x86_64/src/s3.rs`: wake stub copied to phys 0x7400 (real -> protected -> long mode on a temporary PML4 below 4 GiB
  that copies the kernel half and identity-maps 0x7000), parameter block at 0x7D00, own GDT inside the stub, optional PC-speaker beep
  (`pm.s3_beep=1`) and MISC_ENABLE restore (Intel). `pm_s3_lowlevel` (setjmp-like: 0 = platform call returned, 1 = woke),
  `pm_s3_resume64` restores CR4/EFER/XCR0/CR0/CR3/RSP in asm, then `s3_restore_cpu` (enable_sse, PAT, GDT/TSS (clears BUSY), IDT,
  SYSCALL MSRs, FS/GS/KGS bases, TSC_AUX).
- `ioapic::pm_save/pm_restore`, `timer::pm_rebase` (EPOCH_TSC, GRID_TSC, ONESHOT/LAST_IRQ/LAST_TICK of every CPU), `rtc::clear_day_alarm`
  (only when FADT DAY_ALRM == 0x0D), `smp::set_nosmp` + boot knob `nosmp`, `acpi_power::facs_va`.
- `kernel/src/pm_s3.rs`: the sequence. refuse unless `pm.s3=1`, valid `\_S3_` (typ != `\_S5_`), FACS signature ok, exactly 1 CPU
  online, BSP; sync_all + klog flush; device hooks (`PM_S3` flag: pci saves without clobbering, restores unconditionally);
  FACS waking vector; everything fallible happens BEFORE `_PTS`; `_TTS/_PTS/_SST(3)`; cli; ioapic/CPU save; `enter_s3` = ACPICA
  legacy sequence (clear WAK/fixed/GPE status, GPE_EN=0, PM1_EN=RTC|PWRBTN|PCIEXP_WAKE_DIS, SLP_TYP write, wbinvd, SLP_EN, 2 s wait
  for WAK_STS). After the wake: PM1_STS logged (RTC/PWRBTN/WAK), SLP_TYP=`\_S0_`, apic/ioapic/timer re-init, TSC rebase, realtime
  from the RTC, canary check (halt with the gate closed on mismatch), status/enable restore, sti, then `_SST(2)/_WAK(3)/_SST(1)`
  (`_WAK` ONLY here: after a real wake, or when the platform ignored SLP_EN), FACS vector cleared, `_TTS(0)`, kacpid resumed, devices resumed.
- `pm_test=core`: the same up to the sleep, then the CPU restore in place (no platform sleep, no `_PTS`/`_WAK`).
  `pm_test=platform/processors` still ENOSYS (platform is unsafe on HP: `_WAK` without S3 = SMI 0xEA91 = reset).
- Knobs (all inert without `pm.s3=1`): `nosmp`, `pm.s3_beep=1`, `pm.s3_wak=0` (skip `_WAK`), `pm.s3_reset_after=N` (reset N s after a
  resume; bring-up helper because the root stick is gone until s3xhci), `pm.s3_reset_flush=1`.

## Evidence
- QEMU x86_64 (TCG, `--cmdline "pm.s3=1 nosmp pm.test=core"`): all hooks suspend/resume, `core restore done`, TSC delta 0xb65f9, 263 PCI dwords verified.
- QEMU x86_64 real S3 (`pm.s3=1 nosmp`, `echo +6 > wakealarm; echo mem > state`): `RESUMED from S3; PM1_STS 0x8401 (RTC 1 WAK 1), TSC delta 0x15ab6c619,
  slept ~6 s`, `_WAK(3)` ran after the wake, all device resume hooks ok, shell continued (`S3_RC=0`). QEMU reset the virtio devices
  yet the root disk kept working (the QEMU wake path restored it), so no virtio-resume was needed there.
- Default x86_64 boot (`suspendtest`) and aarch64 boot (`suspendtest`, `cat /sys/power/state`): pass, 0 panics.
- Laptop (trial f838885bd17d, kernel tag s3core, `pm.s3=1 nosmp pm.s3_beep=1 pm.s3_reset_after=60`): `/sys/power/state` = `freeze mem`.
  Attempt 1 (trigger in a background job) never started the S3 (the remote shell killed it; klog had only the alarm line), laptop untouched.
  Attempt 2 (foreground, alarm +15 s): the laptop went off the network and was still unreachable ~4 min later (no ping, no ssh), and the
  60 s reset helper never fired. NOT retried (rule). Laptop is left on the trial kernel, needs the power button; the next boot
  falls back to good (trial reached init).

## Open / suspects for the laptop failure (no serial, no klog after the cut)
1. The wake never happened (RTC alarm did not set RTC_STS / PM1_EN write layout on this PCH; `_PTS` EC state) -> machine sleeps until the button.
2. It woke, the wake stub or `pm_s3_resume64` hung (no way to see; the beep (pm.s3_beep) could not be heard remotely).
3. It resumed but `devs_resume`/klog/network are dead: xHCI (root stick), e1000e and iwlwifi are not re-initialised after power loss (s3xhci,
   s3nvme, s3iwlhda lanes). The reset helper would then wait in sched::kthread::msleep, which needs the timer: check this first
   (a hang before it would mean the TSC rebase / LAPIC timer restart).
Next boot on the good kernel: `remote.py logs` (klog-all.txt) holds the text up to the pre-sleep klog flush: look for `[PM] S3: entering sleep now`
and the `_PTS` line.
