# lane/hda — 2026-10-09 — Intel HD Audio playback (sound on the real PC)

Branch `lane/hda`, base main `d0061ae`. Not pushed, not merged.

Goal: sound on the user's PC (Kaby Lake desktop, Sunrise Point-H PCH) so
Firefox/YouTube and DOOM play through PipeWire. The PC boot logs
(nvrm-boot2..6.log) list the HDA controller as **8086:a170** (Sunrise Point-H
HD Audio, 00:1f.3, class 0403). The iGPU is off (no 8086:59xx display
function), so there is no Intel HDMI codec. The RTX 3070's HDMI function
**10de:228b** is listed and skipped. The codec is not known yet; the driver
logs its vendor:device id.

## What was built

- **`drivers/src/hda.rs`** (new): an Intel HDA controller and codec playback
  driver. Written from the HDA spec rev 1.0a; Linux and BSD were read as
  documentation only.
  - **Probe**: class 0403, Intel first, then other vendors (GPU HDMI
    functions from 10de/1002 are skipped with a log line), then Intel class
    0401 (the SST/SOF DSP variant). For 0401 it tries the legacy HDA
    interface and says so: it logs `audio DSP (SST/SOF) mode; trying its
    legacy HDA interface`, plus `(audio-DSP class 0401, legacy HDA mode)` in
    the summary.
  - **Intel PCH setup**: TCSEL=0, and snooped DMA: DEVC (0x78) bit 11 is
    cleared on PCH parts, not on ICH-era ones like QEMU's model.
  - **Bring-up**: memory decode, bus master and INTx-disable on;
    GCTL.CRST reset; waits up to 100 ms for STATESTS.
  - **Codec commands**: CORB/RIRB (256 entries) with RINTCTL set but
    INTCTL=0, which QEMU needs (see below). If a ring command times out it
    falls back to the immediate-command interface automatically.
  - **Position**: a DMA position buffer is set up for diagnostics; the
    driver reads LPIB.
  - **Codec walk**: every codec in STATESTS, root → AFG (set to D0) →
    widgets: capabilities, pin caps, config defaults, connection lists
    (short and long form, ranges), amp caps (with the override bit).
    Everything goes to the log.
  - **Paths**: output pins are those whose BIOS config default says
    line-out, speaker or HP, connectivity not "none", analog. Two fallback
    passes cover bad pin configs. Each pin gets a BFS path (at most 5 hops)
    to an analog DAC through mixers and selectors. **Every chosen DAC uses
    the same stream tag**, so rear line-out, front headphone and speaker all
    play the same stereo signal. There is no auto-mute and no jack
    retasking.
  - **Programming the path**: connection selects; output and selector amps
    unmuted at 0 dB (the amp's offset step). Mixers unmute only the inputs
    some path uses, so the analog loopback is muted. Pin control OUT_EN
    (+HP_EN on headphone pins), EAPD on every EAPD-capable pin, D0 on
    widgets with power control. Pin control and amps are read back and
    logged.
  - **Stream**: the first output stream descriptor, tag 1, a 64 KiB cyclic
    BDL (16 × 4 KiB) below 4 GiB, 16-bit stereo. 48 kHz and 44.1 kHz run
    natively (any rate the DAC advertises). Other rates are linearly
    resampled to 48 kHz, and mono is duplicated.
  - **Underruns**: software keeps `played` (from LPIB deltas) and `written`
    counters. On every update it zeroes the region the DMA has already
    fetched, so an underrun plays silence rather than looping old audio. A
    starved writer is re-synchronised 16 KiB ahead (`RESYNC_PRIME`, the
    counterpart of virtio's top-up watermark; see "Bugs found").
  - **No interrupts**: the audio server's 100 Hz tick pump polls, which is
    all a ring-buffer stream needs. MSI is not used.
- **`servers/pipewire`**: the playback device is now an enum,
  `Backend { Virtio, Hda }`, behind the same calls. Everything above it
  (spool, single-writer rule, `/dev/pipewire`, GET_DELAY) is unchanged, so
  PipeWire's leandros-snd-sink, aplay and DOOM need no changes.
  - `init(cmdline)`: `snd.backend=auto|virtio|hda`. `auto` means
    virtio-sound when present, otherwise HDA.
  - GET_DELAY uses the backend's exact queued bytes.
  - New **ioctl 0x103 SND_GET_INFO** returns the driver state as text
    (backend, controller/codec ids, pins, LPIB/posbuf, counters).
- **`userland/sndtest/sndtest.c`** (zig/musl, like nettest):
  `sndtest info | tone [hz] [s] [rate] | lr | all`. It plays through
  `/dev/pipewire` exactly like the PipeWire sink: SET_PARAMS, write,
  GET_DELAY. `all` plays a 2 s 440 Hz tone on both channels, 1 s left only
  at 440 Hz, 1 s right only at 660 Hz, then 1 s at 44.1 kHz, and prints
  `sndtest: SUMMARY PASS|FAIL`.
- **`/bin/snd-autotest`** (`userland/sndtest/snd-autotest.sh`): init starts
  it when the cmdline has **`snd.test=1`** (`autorun_snd()`, separate from
  `autorun()` and from the r8169 lane's net autotest). It runs `sndtest all`
  twice.
- **`scripts/run-qemu.sh --hda[=output|duplex|micro]`**: ich9-intel-hda plus
  a QEMU codec instead of virtio-sound (virtio stays the default).
  `LEANDROS_AUDIO_WAV=<file>` records to WAV in run-qemu.sh too.
  `driver.py` accepts `LEANDROS_SND=hda|hda-micro|...`.
- **`.claude/skills/run-leandros/sndwav.py <wav> --expect`**: segments a
  capture and checks the sndtest pattern: frequency within 3 Hz, the silent
  channel at least 30 dB down, duration within 15 %.
- **`scripts/nvidia-test-stick.sh --cmdline snd.test=1`** was already
  accepted; it is now documented, and the script prints what to listen for.

## On the PC

```
./scripts/nvidia-test-stick.sh /dev/diskN --cmdline snd.test=1
```

- Plug the speakers into the **rear GREEN jack** (line out), and/or
  headphones into the front panel jack. Every analog output plays the same
  signal.
- Boot. About 5 s after the login prompt you should hear this twice: a 2 s
  beep on both sides, a beep on the LEFT only, a higher beep on the RIGHT
  only, then a 1 s beep on both sides.

Expected screen and log lines (QEMU values shown; on the PC expect
`8086:a170` and probably `10ec:08xx`):

```
[HDA] controller 8086:a170 at 00:1f.3, CORB/RIRB command interface
[HDA] codec 0: 10ec:0887 rev 0x... subsystem ........ (Realtek ALC887)
[HDA] output pin 0x14: jack rear green line-out [01014010] path 0x14->0x0c->0x02 jack:plugged
[HDA] output pin 0x1b: jack front green headphone [0221401f] path 0x1b->0x0c->0x02 jack:empty
[HDA] DACs [2] rates 0x..., stream descriptor 4 tag 1
[PW] playback device: Intel HD Audio
snd.test=1: starting /bin/snd-autotest in the background
sndtest: SUMMARY PASS (tone ok, left ok, right ok, 44.1k ok)
==== snd-autotest: done (sndtest exit code 0) ====
```

Read the log back with `grep -a 'HDA\|sndtest\|snd-autotest\|\[PW\]' nvrm-boot1.log`.
The full widget dump (`[HDA]   nid 0x.. ...` lines) is in the log for
offline path analysis.

### Decision tree

- **No `[HDA]` lines at all, or `no HD Audio controller`**: the BIOS has the
  onboard audio disabled ("HD Audio Controller" / "Azalia" = Enabled), or
  the PCI scan missed it.
- **`registers read all-ones`, or `GCTL.CRST did not set`**: the controller
  is powered off or in D3. Check the BIOS. It may need PCI PM D0 (not
  implemented).
- **`no codec answered the link reset (STATESTS = 0)`**: the codec was not
  powered or released. Usually BIOS "HD Audio" set to Disabled or Auto with
  a DSP; or the board needs a longer reset hold.
- **`CORB/RIRB command ... timed out; switching to the immediate command
  interface`**: harmless if the codec lines follow. If immediate also
  fails, `cmd_timeouts` in `sndtest info` grows.
- **`no codec with an analog output pin + DAC path`**: the pin config
  defaults are odd. Send the widget dump; the fix is a pin quirk.
- **SUMMARY PASS but silent**: DMA runs, so the problem is the analog path.
  - Check `jack:` on the output-pin lines. `plugged` on the jack you used
    means the routing is right and it is amp/mute/EAPD.
  - Compare the `pin 0x.. readback: pinctl 0x40 ...` lines: pinctl should be
    0x40 or 0xc0, and the DAC amp should be non-muted (bit 7 clear).
  - Some boards gate the line-out amplifier with a codec GPIO (laptop-style
    quirk, not implemented). The widget dump plus the codec subsystem id
    identifies the board.
- **SUMMARY FAIL with `DMA progress: played 0`**: the stream does not run.
  - `stream: run=false` or `sts 0x08/0x10` means a FIFO or descriptor error,
    which points to DMA reach or snoop. Look for the
    `PCH snoop enabled (DEVC ...)` line.
  - `lpib 0` with `posbuf` advancing would mean LPIB is broken. The driver
    reads LPIB; switching to posbuf is a small change.
- **Wrong jack** (sound only on headphones, or only on the rear): only
  pins the BIOS marks as outputs are used. The output-pin lines show which
  ones; the rear surround jacks (black/orange/grey) also carry the front
  stereo.
- **Crackling or dropouts**:
  - Count `[HDA] writer starved #N` lines and the `starved` counter. Each
    playback end counts once; more means the producer is late (scheduler),
    not the hardware.
  - FIFO errors (`stream status 0x08`) would point to DMA latency or snoop.
  - Constant crackle with no starvation suggests a wrong format/rate pair.
    Check `SET_PARAMS ... -> hw ...`.
- **The PipeWire session plays nothing but sndtest works**: the session's
  sink must open `/dev/pipewire`. Its description still says "Virtio Sound
  Output" (cosmetic). `wpctl status` should list it as the default sink.

## Bugs found during the lane

1. **QEMU's intel-hda stops fetching CORB entries once RINTCNT responses
   are pending**, unless RIRBCTL.RINTCTL lets it raise RIRBSTS.RINTFL. With
   interrupts off, the second command would time out. RINTCTL is set and
   GIE stays 0; each response read clears RINTFL. Real controllers do not
   block, so this costs nothing there.
2. **An empty queue starved PipeWire's sink.** The sink's DLL targets 4096
   frames of delay. virtio always reports at least 16 KiB (its silence
   top-up); HDA reported about 512 B, and the DLL climbs from there far too
   slowly. Measured: the delay stuck at 128 frames, 137 "underruns" in 471
   cycles, and 3–6 discontinuities in 10 s. The fix is that the resync
   primes 16 KiB of silence, the same latency as virtio. After it: 0/0.
3. The starvation counter counted idle resyncs about 11 times a second. It
   now counts only after a producer has queued PCM.

## Risks / not done

- **Real Realtek graphs are untested.** QEMU's codecs are one DAC → one pin
  with no mixer or selector. The mixer, selector and fallback code is
  written to the spec but has never run against real hardware. The widget
  dump in the log is there so it can be fixed offline.
- **No codec-specific quirks** (Realtek COEF writes, GPIO amp enables).
  Desktop ALC887/892/1150/1220 need none for basic playback in Linux's
  generic parser, apart from EAPD, which is done.
- **No interrupts or MSI**: polling at 100 Hz from the tick pump. LPIB
  wraps are handled up to 341 ms of missed ticks.
- **No jack detection or auto-mute**: all outputs play at once. Pin sense
  is logged once at boot.
- **No volume control in hardware**: amps are at 0 dB, and PipeWire applies
  software volume as before.
- **No PCI PM**: the driver assumes D0. No runtime suspend.
- The sink's node description still reads "Virtio Sound Output".
- Capture is not implemented.
- On real hardware, LPIB versus the DMA position buffer is untested. Linux
  uses LPIB for playback on SKL+.
