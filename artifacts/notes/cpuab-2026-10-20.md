# cpuab 2026-10-20: relibc A/B for the P9 YouTube sys-time regression

Same kernel (da51b45e, x86_64; A and B kernels differ by 6 bytes, a build stamp), laptop, one YouTube run each
(p9 m.sh hw, 30.4 s window, panel lit). Only the relibc version differs.

| build | relibc | total CPU | user | sys | firefox | Web Content | RDD |
|---|---|---|---|---|---|---|---|
| A | 10ef96ee | 212.8% | 81.8 | 130.9 | 76.3% | 51.3% | 19.6% |
| B | 9928b292 | 243.8% | 91.6 | 152.2 | 83.4% | 64.7% | 22.4% |
| old good (ref) | 2d54349a era | 211-228% | | ~132 | | | |

Per-call kernel cost, A to B (us/call): Web Content recvmsg(47) 85.6 -> 113.2, firefox recvmsg 73.9 -> 86.5,
Web Content sendmsg(46) 92.8 -> 103.4, firefox sendmsg 62.7 -> 76.2. In-syscall ms/s: firefox 426 -> 491, Web Content 303 -> 395.

## Verdict
A matches the old good numbers, and B is about 15% higher (+21 points of sys). The regression is in relibc, not the kernel.
10ef96ee..9928b292 is a single commit: `9928b292 poll: use the kernel's ppoll on Linux instead of a per-call epoll instance`.
Caveat: there is one sample per build. Next step: profile ppoll's kernel path (the wake fan-out per fd and the extra
recvmsg/sendmsg cost) against the old epoll path, or revert 9928b292 on relibc master.
Note: the first A attempt was lost when the laptop battery died (user rebooted). A was rerun.
