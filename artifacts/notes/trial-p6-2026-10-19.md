## 2. VA-API on (user.js + `LIBVA_DRIVER_NAME=iHD`)
The prefs were added to `z5iqf7sn.default-release/user.js`. **The original user.js has been restored**, because with VA-API on, YouTube no longer plays.

**Result: RDD deadlocks while opening the first VA-API decoder in 6 of 7 launches.** YouTube then picks H.264 (avc1) and never plays: wifi RX is 0, no RDD CPU, exec_vcs +0.
- MOZ_LOG `sync,timestamp,FFmpegVideo:4/5` shows: `Initialising VA-API FFmpeg decoder` -> `DMABuf is enabled` ->
  `GetAcceleratedFormats()` -> `Supported accelerated formats: h264 vp8 vp9` -> **stops**.
  It never reaches `VA-API FFmpeg init successful`, so the hang is in system-libavcodec setup/`avcodec_open2` (Firefox holds `FFmpegDataDecoder::sMutex` there).
- `/proc/sysstat`: `MediaSupervisor #1` sits in `futex` (sc 202) for more than 300 s. No other RDD thread is runnable, and no ffmpeg worker or MediaPDecoder thread exists. `kill -CONT` does not unstick it.
- The hang happens with or without `widget.dmabuf.force-enabled`, with or without MOZ_LOG, and also with `media.mediasource.webm.enabled=false` (H.264 is then the first decoder, with no VP9 decoder before it). So it is not a race with the VP9 decoder's shutdown.
- **The one successful launch** (sync log, PDM:5/FFmpegVideo:5/Dmabuf:4) played 1280x720 H.264 at 60 fps on vcs0 zero-copy:
  `VA-API Got one frame output`, `ImportPRIMESurfaceDescriptor` NV12, the parent `CreateEGLImage ... Success`.
  In a 15 s probe: **exec_vcs +834, busy_vcs_ms +1965, RDD 19.5 %** (MediaPDecoder ×2 ~5.5 %, MediaSupervisor 5.5 %, IPC 2.9 %),
  firefox 67.7 %, Web Content 51.4 %, total 284 %. Verbose sync logging inflated these numbers, and the stream is 720p60 H.264, not the
  baseline's VP9, so this is not a clean A/B.
- The parent's capability broadcast still says `RDD support=H264 SW`, because the HW flag is only set after a decoder succeeds.

## Prefs/env a lane would make default (once the hang is fixed)
- user.js / leandros-prefs.js: `media.hardware-video-decoding.enabled=true`, `media.ffmpeg.vaapi.enabled=true`,
  `media.hardware-video-decoding.force-enabled=true` (needed; ffvpx otherwise logs "Hardware WebRender is off, VAAPI is disabled").
  `widget.dmabuf.force-enabled` was not needed: `DMABuf is enabled` showed up without it.
- env: `LIBVA_DRIVER_NAME=iHD`. `/bin/firefox` already exports `MOZ_DISABLE_RDD_SANDBOX=1`.
- Before that: root-cause the futex hang. Next step: add the futex uaddr to the `/proc/sysstat` `w` line, or dump the
  user stack of the blocked thread, and map it with `/proc/<rdd>/maps`. Then check pthread_once/mutex in libavcodec.so.60 and iHD
  against a lost-wakeup kernel bug. `ffmpeg -hwaccel vaapi` on the CLI (P5b) does not hang.
