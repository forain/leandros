# lane/xhci — 2026-10-05

Goal: a correct, memory-safe xHCI driver with a `BulkTransport` API, as the
host-controller half of "boot from a USB stick" (lanes `blkroot`, `usbmsc`,
`usbharness` do the rest).

## H1 verdict: CONFIRMED — the July "delayed corruption" was a stack overflow

Evidence:

- `size_of::<usb::xhci::Xhci>()` at 7d114ce = **573,568 bytes** (measured with a
  compile-time array-length trick on the kernel target; `SlotData` = 2,240 B,
  `Option<Ring>` = 32 B, × 256 inline slots). The kernel stack is
  `PAGE_SIZE << KERNEL_STACK_ORDER(5)` = **128 KiB**, a plain buddy block with
  no guard page; the only check is a canary at the bottom, verified on
  *syscall return*, which the init task never reaches before the damage.
- `Xhci::new()` returned `Self` by value and built `slots` with
  `core::array::from_fn`. Rust has no placement-new, so even `Box::new(Xhci::new())`
  materialises the value on the stack first. Constructing one writes ~445 KiB
  below the bottom of the 128 KiB stack, into whatever buddy blocks sit there.
- That matches every symptom in `usb_hcd.rs`'s old comment and commit
  0366255: corruption "elsewhere in the kernel afterward", only "with the
  actual live hardware interaction" (the struct was only built on that path),
  not reproducible with "an equivalent-duration delay or buddy footprint" (those
  tests never built the struct), and an apparent sensitivity to PORTSC timing
  (`hub.rs::settle()`), which only moved where the overflow landed.
- `scripts/check-stack-frames.py` (budget 48 KiB) did not exist in July; it
  would have refused that kernel.

The rewrite pins it: `const _: () = assert!(size_of::<Xhci>() < 1024)` and
`size_of::<Slot>() < 512` in `drivers/usb/src/xhci/mod.rs`. The largest USB
frame in the new kernel is `usb::probe_xhci` at 1,696 B (aarch64).

Secondary corruption sources in the old code, also confirmed by reading it
(each would bite on real hardware even without H1):

- **Use-after-free by DMA after a "timeout"**: every wait was a spin count
  (1,000,000 iterations ≈ 1–3 ms on real CPUs). `set_address`,
  `set_configuration`, `get_*_descriptor` freed their input-context / data
  pages after the spin count ran out, with the command or TD still live — the
  controller would then write into a page the allocator had handed to
  someone else.
- **DCBAA[slot] never written**: the controller writes the output device
  context through DCBAA[slot] = 0, i.e. to physical address 0.
- **Stack addresses as DMA targets**: `ep0_control_in` put `buf.as_ptr()` (a
  kernel virtual address on the stack) into the Data Stage TRB.
- **Event ring consumer wrapped at 255** while the ERST advertised 256 TRBs →
  consumer/producer desync after 255 events.
- `CONFIG.MaxSlotsEn` never set (Enable Slot cannot succeed), command
  completions not matched to their command TRB, completion codes ignored,
  speed/port/MPS0 hard-coded to HS/port 1/64, `PORTSC_RW_MASK` included LWS
  (every port write could commit a stale link state), slot state read from
  the wrong bits, 64-bit MMIO writes.

## What was built

`drivers/usb/src/` (crate `usb`, now a dependency of `drivers`):

| file | content |
|---|---|
| `platform.rs` | clock / relax / log hooks (`usb` sits below `sched`); every wait is a `Deadline` on `sched::monotonic_ns`; without hooks a 1 µs-per-read fallback clock still bounds every loop |
| `dma.rs` | `DmaBuf`: buddy block, naturally aligned (≤ 64 KiB never crosses a 64 KiB boundary), zeroed, `dma32` → `mm::buddy::alloc_below(order, 4 GiB)`, freed on Drop; `dma_wmb`/`dma_rmb` + `sync_for_device/cpu` hooks |
| `transport.rs` | `UsbErr` + `BulkTransport`, exactly the agreed signature |
| `xhci/regs.rs` | register map; every MMIO access is one 32-bit `ldr`/`str` from inline asm on aarch64 (no writeback forms → no HVF `isv` abort); 64-bit registers written lo then hi |
| `xhci/ring.rs` | producer ring (256 TRBs + Link/TC, first TRB of a TD published last), event ring (256 TRBs, one-entry ERST, CCS toggles at 256), command-abort no-op patching |
| `xhci/context.rs` | CSZ-aware context accessors (32- or 64-byte entries), EP/slot field builders, interval encoding |
| `xhci/mod.rs` | the controller (below) |
| `selftest.rs` | raw BOT test over any `BulkTransport` |
| `lib.rs` | `probe_xhci`, `devices`, `mass_storage_devices`, `mass_storage_count` |

Controller bring-up (`Xhci::init`): USBLEGSUP BIOS→OS handoff (1 s, then
forced) and SMI disable in USBLEGCTLSTS; Supported-Protocol caps → USB2/USB3
per port + slot type; stop a firmware-left-running controller (R/S=0, wait
HCH); HCRST (wait HCRST=0 and CNR=0); MaxSlotsEn = min(HCSPARAMS1, 64);
DCBAA; scratchpad array + pages (HCSPARAMS2, PAGESIZE) in DCBAA[0]; CRCR;
interrupter 0 with IMAN.IE=0 / USBCMD.INTE=0 (polled); R/S=1; port power if PPC.

Enumeration (root ports only, hubs out of scope): 100 ms debounce, second pass
at +200 ms. USB2 port: PR → PRC, 10 ms TRSTRCY. USB3 port: wait for PED (link
training), warm reset if it doesn't come up. Clear change bits writing only
PRESERVE bits (PP/PIC/WCE/WDE/WOE — never PED, PR, LWS). Enable Slot (slot type
from the protocol cap) → contexts + EP0 ring + DCBAA[slot] → Address Device
(speed, root port, MPS0 by speed) → GET_DESCRIPTOR(8) → Evaluate Context if
bMaxPacketSize0 differs (SS: 2^n) → full device + config descriptors → strings
(best effort) → for a class 08 / protocol 0x50 interface in **any alt setting**
(prefers subclass 06; UAS-only 0x62 is reported unsupported): Configure Endpoint
(slot context copied from the output context, Context Entries, bulk type, MPS,
SS max burst from the companion, Interval 0, avg TRB 3 KiB) → SET_CONFIGURATION
→ SET_INTERFACE if alt ≠ 0. One lsusb-style line per device:

    [USB] Bus 001 Device 001: ID 46f4:0001 QEMU QEMU USB HARDDRIVE [port 1, super-speed (5G), class 08, bulk-only mass storage]

Transfers: the event ring is drained by whoever polls; command completions
are matched by command-TRB pointer, transfer events are filed under
(slot, DCI) and matched by TRB pointer (stale events from cancelled TDs or
post-short-packet duplicates are ignored). Control: Setup(IDT, TRT) +
Data(ISP) + Status(IOC) — no IOC on the data stage. Bulk: through a per-endpoint
bounce `DmaBuf` (callers' buffers are never DMA targets), ≤ 64 KiB per TRB,
up to 16 chained TRBs (1 MiB) per TD with correct TD Size, larger transfers
split into several TDs, a short IN chunk ends the transfer. Completion codes:
STALL → `Stall` (bulk endpoint left halted for the class driver; EP0 recovered
internally), Babble → `Babble`, port gone → `Disconnected`, else
`Other(cc)`. Timeout → Stop Endpoint + Set TR Dequeue before returning; a
failed recovery or command-ring abort halts the controller, so no `DmaBuf`
is ever freed or reused while the controller can still reach it. Slots are
freed only after a successful Disable Slot.

`clear_halt_in/out`: halted → Reset Endpoint (TSP=0) + Set TR Dequeue;
not halted → Stop Endpoint + Configure Endpoint drop+add (the only way to
reset the host sequence state of a live endpoint); then
CLEAR_FEATURE(ENDPOINT_HALT).

`drivers/src/usb_hcd.rs`: PCI class 0C/03/30 on both arches; returns
immediately when there is none. BAR0 sized (decode off), memory + bus master
on, INTx off, mapped with `map_kernel_device(MMIO)`. Intel 7/8/9-series PCH
port routing (XUSB2PR/USB3_PSSEN) as Linux does. `lsusb` now lists the devices.

### Using the API (for the integration lane)

```rust
use drivers::usb_hcd::{mass_storage_devices, BulkTransport, UsbErr, XhciBulk};
// after drivers::usb_hcd::init() (kernel/src/init.rs, after blkdev init):
for mut t in mass_storage_devices() {        // Vec<XhciBulk>, handed out once
    let iface = t.interface_number();
    t.class_control_in(0xFE, 0, iface as u16, &mut lun)?;   // GET_MAX_LUN
    t.bulk_out(&cbw, 5000)?; t.bulk_in(&mut data, 5000)?; ...
}
```

`XhciBulk` is `Send`; it holds an `Arc` to its controller. Transfers are
synchronous and poll with `sched::yield_now` between polls, so they must be
called from task context (not IRQ). Debug: kernel feature `usb-debug`
(verbose trace + boot self-test), or `drivers::usb_hcd::set_debug(true)`
before `init()`.

### Other fix found on the way

`drivers/src/pci.rs`, x86_64 `pci_write_config_16/32`: the asm overwrote `eax`
(address → data) but declared it input-only, so LLVM reused `eax` as the
*address* of the next config access. BAR sizing read back from bus 255
(all-ones → "16-byte BAR"). Now `inout("eax") address => _`. Any earlier
write-then-read sequence on x86 could have hit this.

`mm/src/buddy.rs`: new `alloc_below(order, limit)` (free-list walk). Retrying
`alloc` was tried first and failed outright on a 4 GiB aarch64 guest: the
allocator hands out high memory first and all 16 retries landed above 4 GiB.

Self-test content (each boot): GET_MAX_LUN (=0), INQUIRY (`QEMU QEMU HARDDISK 2.5+`), an unsolicited bulk IN
(QEMU STALLs → `Stall`, then `clear_halt_in` = Reset Endpoint + Set TR Dequeue + CLEAR_FEATURE),
INQUIRY again, `clear_halt_in/out` on idle endpoints (Stop Endpoint + Configure Endpoint drop/add +
CLEAR_FEATURE), TEST UNIT READY, READ CAPACITY (131072 × 512), READ(10) of 64 KiB (one TRB) and of
192 KiB (three chained TRBs, 256 KiB bounce), equal over the overlap, sector 0 ends in 55AA.

Not exercised by QEMU: a Stop Endpoint on a *running* endpoint after a real NAK timeout (QEMU
storage STALLs instead of NAKing), command-ring abort, CSZ=1, scratchpads, BIOS handoff.

The loop kernels predate two later edits (the Intel PCH routing quirk, inert on QEMU's
1b36/1033 IDs, and a comment in hub.rs); the default-kernel runs above are from the final tree.

## Remaining real-hardware-only risks

- **CSZ=1 (64-byte contexts)**, **scratchpad buffers**, **BIOS handoff/SMI
  disable**, **AC64=0**, **firmware-left-running controller**: all implemented,
  none exercised by QEMU (qemu-xhci/nec-usb-xhci: CSZ=0, 0 scratchpads, no
  legacy cap, AC64=1, OVMF/AAVMF stop the controller at ExitBootServices).
  AC64=0 allocation was exercised by forcing dma32 (all rings/contexts/bounce
  buffers landed below 4 GiB and the self-test passed).
- **Early firmware DMA**: if firmware leaves the controller running, it keeps
  DMAing into firmware-owned memory the kernel may already have reclaimed,
  until `usb_hcd::init()` (after blkdev init) stops it. A quiesce at the very
  start of boot would close that window.
- **Cache coherency**: `DmaBuf::sync_for_device/cpu` are barriers only.
  Correct for x86 and QEMU virt; a non-coherent aarch64 board needs clean /
  invalidate by VA there. The Pi 5's USB is behind RP1 on PCIe, which this
  kernel does not bring up at all (no PCIe on rpi5 builds).
- **Timing**: 100 ms + 200 ms connect windows; very slow USB3 link training
  or a device that needs > 2 s per control request would be missed/failed.
  No hot-plug handling after boot.
- **Hubs**: devices behind a hub (including laptop-internal rate-matching
  hubs on Intel 6-series and later!) are not enumerated. On many real
  machines the external ports *are* behind such a hub on the USB2 side;
  USB3 ports are direct. This is the biggest functional gap for real hardware.
- **Streams/UAS**: UAS-only devices (no BOT alt) are skipped.
- **Locking**: the controller lock is a `spin::Mutex` taken from task
  context; it is never held across a wait, but a holder can be preempted.
  The integration lane should call the transport from one context at a time
  per device (the `&mut self` API already enforces that per transport).
- **AMD/ASMedia/VIA quirks** (Linux xhci-pci quirk table) are not ported.
