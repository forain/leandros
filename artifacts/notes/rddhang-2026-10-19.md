# RDD VA-API init hang: root-cause investigation (2026-10-19)

Status: **NOT closed.** The hang is narrowed to one function call. The exact futex word is not named yet: this kernel cannot report a
futex address remotely, and the laptop's sshd wedged during the first live run (see "Laptop state").

## 1. What the kernel exposes (grep of the tree)
- `/proc/sysstat` `w` lines (`servers/vfs/src/lib.rs` gen_sysstat) give state, syscall nr and in-syscall time. They do **not** give the futex
  address, the futex value or the user PC. `/proc/<pid>/stat` has no kstkeip/kstkesp. There is no `wchan` file, no `syscall` file,
  no ptrace and no `/proc/<pid>/mem`.
- The data already exists in the kernel. `sched::task_rows` (sched/src/lib.rs ~3284) computes `blocked_futex`, `urip`, `ursp` and the
  futex word's value. `sched::dump_tasks` prints `futex=<uaddr>=<value> pc= sp= rax= rdi=` into klog, but **only on Ctrl-T typed on the serial
  line or the VT console** (servers/tty console_intercept_byte), so it cannot be used remotely or from the desktop.
  `dump_group_stacks` is behind the compile-time flag `SC_STATS=false`.
- `/proc/<pid>/smaps` prints no paths (`00:00 0`). Libraries have to be matched by size and file offset.

## 2. Where it hangs (Firefox 136.0.4 source, hg FIREFOX_136_0_4_RELEASE, confirmed against the staged libxul)
In 136, `InitVAAPIDecoder` calls **`avcodec_open2` BEFORE `GetAcceleratedFormats`**. The order is CreateVAAPIDeviceContext → AllocateExtraData →
avcodec_open2 → GetAcceleratedFormats → **AdjustHWDecodeLogging()** → "VA-API FFmpeg init successful". "Supported accelerated
formats" is printed by a ScopeExit as GetAcceleratedFormats returns. So the trial note's "hang in avcodec_open2" is wrong. The hang is in
AdjustHWDecodeLogging (libxul 0x5d21520, the LIBAV 60 instance), which does:
`getenv("MOZ_AV_LOG_LEVEL")`, `av_log_set_level(DEBUG)` (a plain store), `getenv("LIBVA_MESSAGING_LEVEL")`, then
**`setenv("LIBVA_MESSAGING_LEVEL", "0"|"1", 0)`**. That is the RDD process's first `setenv` ever: software decoding never calls it, and the
ffmpeg CLI has no interposer.
- getenv and setenv resolve to mozglue's env interposer, which the `firefox` executable exports (`setenv` at 0x1fa40). The first
  setenv does `__cxa_guard_acquire` (guard firefox+0x6b6e0, libstdc++, non-private futex), then `dlsym(RTLD_NEXT,"setenv")` (musl's dynlink
  rwlock, private), then `pthread_mutex_lock(gEnvLock)` (firefox+0x6bb20, .bss, normal mutex, private), then musl setenv, which calls `malloc`.
- **malloc is Scudo, not musl and not mozjemalloc**: the `firefox` executable has `NEEDED libscudo.so`. Scudo's HybridMutex uses
  FUTEX_WAIT/WAKE_PRIVATE.
- **The only success also skipped the setenv.** log4 (the one launch that played) shows ffmpeg DEBUG lines from the first decoder on, so
  MOZ_AV_LOG_LEVEL was in its environment. It also shows `libva info` blocks at every later vaInitialize, which libva suppresses once
  LIBVA_MESSAGING_LEVEL=1, so LIBVA_MESSAGING_LEVEL was preset too. Both getenv calls returned non-NULL, and no setenv ran. In the hung
  launches (log1/2/3/5/6) neither variable was preset. This is inferred from the stderr content: no record of log4's launch
  command was found.

## 3. Thread evidence (existing p6 sysstat snapshots)
`ss.txt` RDD 13810 and `ss2.txt` RDD 39322 have the same layout, mapped through `probes2` comm names:

| thread | state | since |
|---|---|---|
| main | poll | starts AFTER the hang (alive) |
| IPC I/O Child | epoll | starts AFTER the hang (alive) |
| AsyncSi~lThread | read | before the hang |
| ProfilerChild | futex | before the hang, 0.18 ms CPU in total |
| **MediaSupervisor #1** | **futex** | **since the hang** (300.9 s), 30-79 ms CPU |
| Timer | futex | created by main **~10 s after** the hang |

- When MediaSupervisor blocked, the only other runnable threads were main and the IPC I/O thread.
- Main created the Timer thread 10 s later. That takes calloc and the musl thread-list lock, so the Scudo locks those calls use and
  `__thread_list_lock` were free after the hang.
- RDD made 81 ioctls in total (one vaInitialize). No `[SYSCALL] ENOSYS` lines, and the only DRM-unimplemented ioctl is GET_CLIENT (greeter).
  The uapi_err entries are GETPARAM probe answers.

## 4. Verdict so far
**(a) A userspace wait inside the first `setenv()` in RDD** is the trigger: 6/6 hangs with it, 1/1 success without it. The candidate words are
gEnvLock (firefox+0x6bb20), the setenv `__cxa_guard` (firefox+0x6b6e0), musl's dynlink rwlock (dlsym), and a Scudo region or TSD mutex.
All are private except the guard, and the guard is uncontended. So:
- Cross-process wake theft is ruled out. With no ASLR, the non-private key "same VA in every process" is real (musl `__thread_list_lock`, Mesa
  simple_mtx, libstdc++ guards), but no non-private word is contended in this window.
- **(b) A lost wake in our kernel is possible but not shown.** The futex.rs register/recheck/commit, wake and requeue paths read as correct.
- **(c) No odd syscall return was seen** in this window.

The remaining question is which word, and who holds it. Ranked guesses: a Scudo mutex taken under gEnvLock, the musl dynlink rwlock (a dlopen in
progress on main), then gEnvLock itself.

## 5. One-lane next step
1. **Kernel diagnostics lane** (small). Add `fut=<uaddr> fval=<word> rip= rsp=` to the `/proc/sysstat` `w` line, reusing `task_rows`. Optionally add
   a root-only `/proc/sysrq-trigger`-style write that runs `dump_tasks` into klog. Map uaddr against the `firefox` .bss (0x6b660..0x6da38),
   libc.so, libscudo.so and libxul with `/proc/<rdd>/smaps` offsets. The value also identifies the lock type: musl normal mutex 0x80000010,
   musl rwlock writer 0xffffffff, Scudo HybridMutex 2, libstdc++ guard 0x100|0x10000.
2. **Same-boot A/B, no code needed:** launch with `LIBVA_MESSAGING_LEVEL=1 MOZ_AV_LOG_LEVEL=48` preset. Expect 0 hangs if section 2 is right.
   **Ship-ready workaround:** export `LIBVA_MESSAGING_LEVEL=0` in `/bin/firefox` (`ports/firefox/firefox.sh`) next to `LIBVA_DRIVER_NAME=iHD`.
   That removes RDD's only setenv. Firefox then never reaches the hanging path, whatever the word turns out to be.
