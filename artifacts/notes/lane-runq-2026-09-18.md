# lane/runq — RUN_QUEUE contention on the 100 Hz tick (2026-09-18)

Item (TODO.md "Open work"): the poll-deadline tick's `RUN_QUEUE.try_lock()` fails
">50 %" of ticks with the greeter desktop idle, so every timed poll/epoll wake pays
1–2 ticks of retry latency; "the long holder has not been found".

## Instrumentation (kept, in `sched/src/lockwatch.rs`)

`TrackedMutex::lock`/`try_lock` are `#[track_caller]` and, for RUN_QUEUE, record the
acquire site (`core::panic::Location`) and acquire time. A tick-context attempt that
fails charges the failure to the site holding the lock at that instant, with the hold's
age and the holder CPU's pid/syscall (`note_tick_try`). `HOLD_PROFILE` (const, default
`false`) additionally feeds a per-site hold-count / avg / max / 7-bucket duration
histogram on every release. Ctrl-T (`dump_tasks`) prints it all as a `[RQPROF]` block,
including tick attempts/failures and `try_lock_spin` stats.

## What the histogram said (aarch64/HVF, greeter idle 68 s, `HOLD_PROFILE=true`)

```
[RQPROF] tick try_lock: attempts=6659 failed=549 self=0 free=197 | age-at-fail: 345 5 0 0 1 1 0
[RQPROF] lib.rs:2737 unblock_port          holds=11678093 avg=374ns max=4.69ms | tickfail=175
[RQPROF] lib.rs:1057 current_reply_port    holds=11677323 avg=43ns              | tickfail=21
[RQPROF] lib.rs:1356 block_on_port_prepare holds=11678442 avg=44ns              | tickfail=53
[RQPROF] lib.rs:1363 block_on_port_cancel  holds=11679062 avg=37ns              | tickfail=27
[RQPROF] lib.rs:2870 scheduler pick        holds=1222032  avg=364ns             | tickfail=54
[RQPROF] lib.rs:2372 lock_leader_as        holds=1363007  avg=55ns
[RQPROF] signal.rs:108 has_deliverable_sig holds=2384944  avg=39ns
```

- **Failure rate was 8.2 %, not >50 %** (549/6659; one attempt per tick, since a timed
  waiter is due on every tick with the desktop up). The ">50 %" figure in the wave note
  was an impression from the timerfd lane, never a count. REFUTED.
- **There is no long holder.** 99.9 % of holds are < 1 µs; at the moment of a failed
  tick the hold was < 1 µs old in 345/352 attributed cases (and 197 more found the lock
  already free again). The rare ms-scale maxima are host vCPU preemption of the holder.
- **The cause is traffic, not duration:** ~760 k RUN_QUEUE acquisitions/s on an "idle"
  desktop, a ~9 % duty cycle, which a one-shot `try_lock` loses ~8 % of the time. Four
  of those acquisitions come from every synchronous server call (`vfs::call_port` →
  `port::send` → handler → reply): `current_reply_port` (lock + scan for own task),
  `unblock_port` on the reply port (a full 256-slot scan that never finds anyone — the
  owner is the sender itself), `block_on_port_prepare` and `block_on_port_cancel` for a
  park that never happens because the reply is already queued. cosmic-comp's software
  render loop issues ~170 k such calls/s (it is `Running` on one CPU whenever the
  greeter is up: mmap/munmap/epoll churn), hence 4 × 11.7 M holds in 68 s.

## What changed

1. `ipc/src/port.rs::send` — skip `sched::unblock_port` when the port's owner is the
   current task (only the owner may receive, and it is running, so nobody is parked).
2. `servers/vfs/src/lib.rs::call_port` — try `recv_as` before the prepare/cancel park
   protocol; a synchronous reply is taken with zero RUN_QUEUE holds.
3. `sched` — `CURRENT_REPLY_PORT[cpu]` published at dispatch and by
   `set_current_reply_port`; `current_reply_port()` is now two relaxed loads.
4. `sched::lockwatch::TrackedMutex::try_lock_spin(max_ns)` — bounded (50 µs) wait used
   by `service_poll_deadlines` and `try_wake_poll_tagged`. Holds are sub-µs, so waiting
   a few hundred ns beats deferring a wake by a 10 ms tick; the bound keeps the
   no-deadlock property of the old one-shot `try_lock` (worst case: 50 µs, then the same
   deferral as before). `self=0` in every run confirms CPU0 never holds RUN_QUEUE when
   its own tick fires.

Result, same scenario (greeter idle 60 s):

| | before | after |
|---|---|---|
| tick attempts / failed (aarch64/HVF) | 6659 / 549 (8.2 %) | 5852 / 3–7 (0.05–0.12 %) |
| spun ≤ bound / gave up | – | 275–307 / 3–7, max spin 6–28 µs |
| RUN_QUEUE holds per sync server call | 4 | 0 |
| tick attempts / failed (x86_64/TCG, 90 s) | not measured | 8106 / 3 (0.04 %) |

## Regression test: `polltest` `poll_timeout_wake_latency`

1000 × `poll(idle pipe, 10 ms)` timed with `clock_gettime(CLOCK_MONOTONIC)`; prints
overshoot p50/p90/p99/max in µs and the count of >1-tick-early returns; passes when
`early == 0 && p90 <= 5 ms && p99 <= 20 ms`.

| kernel | accel | p50 | p90 | p99 | max | result |
|---|---|---|---|---|---|---|
| main + instrumentation only | aarch64/HVF | 10 | 9494 | 21002 | 40445 | FAIL |
| fixed | aarch64/HVF | 0 | 47–113 | 2030–2433 | 2430–23756 | PASS ×4 |
| fixed | x86_64/TCG | 0 | 72–214 | 2713–7525 | 5983–10780 | PASS ×3 |

(The one 23.7 ms max on HVF was a single 2-tick slip in the first post-fix run, while
the greeter was still starting; the remaining ~2 ms p99 is tick-IRQ latency on CPU0
behind a long IRQ-masked syscall of the compositor, not lock contention.)

Other suites after the change: aarch64/HVF and x86_64/TCG polltest 6/7 (see below),
x86_64/TCG epolltest 11 PASS / 0 FAIL, wakepolltest 17/0, vfstest 39/0, timertest
10/0, pthreadtest 5/0; greeter paints on aarch64 at 60 s; no `[WDOG]`/panic lines.
