# lane/smapx86 (2026-10-23) — L7.4 x86 half FIXED (SMEP + SMAP)

Commit 8fea3dea.

## What
- CR4.SMEP (bit 20) / CR4.SMAP (bit 21) set in `enable_sse(bsp)` on the BSP and every AP, each only when
  CPUID.(7,0):EBX bit 7 / bit 20 says so (max leaf checked first). The `pan=strict|audit|off` knob now also
  drives SMAP (read before x86 arch init); a BSP without SMAP drops PAN_MODE to 0 so no stac/clac (#UD) runs.
  SMEP is on whenever present. Kaby Lake (laptop) has both; TCG `-cpu max` (driver default) has both.
- `sched::uaccess`: copy / cmpxchg32 / load32 save RFLAGS in r8, `stac` (gated on PAN_MODE), and close
  through a shared `__uaccess_close` epilogue (also from the fault landings) that `clac`s unless the caller
  already had the window open. `UserAccess` windows stac/clac the same way.
- `cpu_switch_to` saves RFLAGS and restores only AC (new `CpuContext.rflags`, offset 576, asserted) so a
  window survives blocking/preemption and never leaks into another task.
- `fault_common` clacs on entry (gates do not clear AC; ring 3 can set it). SYSCALL FMASK already cleared AC.
- Ring-0 protection fault (P=1) on a user address with AC clear, or an instruction fetch (I/D=1), is
  classified before handle_page_fault: `SMAP violation at <rip> addr <cr2>` / `SMEP violation ...` + panic.
  `pan=audit`: first 64 sightings logged as `[SMAP] audit:` and let through with AC set.
  The `sys_secprobe` probe address kills the task instead (privtest needs it).
- sys_secprobe ops 0-3 now on x86 too; privtest gained x86 cases kernel_smap_traps_raw_access,
  kernel_uaccess_under_smap_ok, kernel_smep_refuses_user_code (on main x86 op 2 was ENOSYS -> fail).
- Raw user accesses that would have panicked on the laptop: i915 uapi `read_user`/`write_user` (49 uses,
  ptr::read_unaligned on ioctl args) and 3 copy_nonoverlapping sites (QUERY data_ptr, PREAD/PWRITE, SSEU
  value) now go through uaccess (EFAULT on a bad pointer); DRM server VFS_WRITE copies via copy_from_user.
- kexec purgatory clears SMEP/SMAP with PCIDE/PGE (new kernel re-enables them).

## Evidence (x86_64 TCG release)
- privtest strict: PASS, `SMAP violation at 0xFFFFFFFF801101E0 addr 0x40010000` (probe, killed),
  `SMEP violation at 0x40011000 addr 0x40011000`, traps since boot 1.
- full x86_64 regress, strict: overall PASS, 0 violation lines.
- aarch64 regress: see report.

## Open
- kexec -e not exercised at runtime with SMEP/SMAP (purgatory change is defensive).
- Laptop not tested: any x86-only driver path not covered by QEMU that dereferences a user pointer raw
  would now panic; boot the laptop with `pan=audit` first if in doubt (logs instead of panic).
