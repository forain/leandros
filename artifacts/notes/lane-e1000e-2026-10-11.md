# lane/e1000e — 2026-10-11 — Intel I219 (e1000e) Ethernet for the new laptop

Branch `lane/e1000e`, base main `571ce20`. Not pushed. Goal: Ethernet on the
user's new laptop (i5-8350U Kaby Lake-R, Sunrise Point-LP PCH, Intel
**I219-LM**, vPro, so the Intel ME/AMT probably shares the PHY) through the
existing `eth0` / `netdev` path, so DHCP, DNS, TCP and Firefox work. The exact
PCI id is not known yet: the first boot logs it
(`[e1000e] found 8086:15d7 PCH_SPT_I219_LM4 (family pch_spt) ...`; on SPT-LP
it is most likely 15d7, 15e3 or 156f).

QEMU has no I219 model, but its `-device e1000e` (82574L) has the same
descriptor/ring/register core, so the driver also binds the 82574L and its
data path is proven there end to end. The PCH-only parts (ME handshakes, ULP
exit, LANPHYPC, PHY pages, K1, LTR, NVM flash, the SPT ring-flush quirk) can
only be proven on the laptop, so the first boot is made maximally diagnostic.

### Ids

All 55 I219 ids of Linux's table (boards pch_spt / pch_cnp / pch_tgp /
pch_adp / pch_mtp, Skylake through Nova Lake) plus 82574L/LA (10d3/10f6).
I217/I218 (pch_lpt) and older are not bound. The family follows Linux's
board, not the name (e.g. CMP LM12 0d53 is an SPT board).

### Driver flow

1. **`init` (boot context)**: first matching device; D3->D0; (82574 only)
   ASPM L0s/L1 off as Linux does; mem + bus master; BAR0; logs CTRL, STATUS,
   CTRL_EXT, EXTCNF_CTRL, and for PCH the **ME view**: FWSM decoded (FW_VALID,
   mode iAMT/ASF, RSPCIPHY = PHY reset allowed/blocked, ULP_CFG_DONE,
   WLOCK_MAC, PCIM2PCI), H2ME, MANC, STRAP, FEXTNVM, PHY_CTRL, and the link
   state the firmware left. MAC from RAL0/RAH0, else NVM words 0-2 (PCH flash
   via the SPT+ registers at BAR0+0xE000, or EERD on the 82574), else random
   locally administered. Rings (256 RX + 256 TX legacy descriptors, 2 KiB
   buffers, below 4 GiB). MSI. Starts `[e1000e]`.
2. **`[e1000e]` thread** (Linux probe + open; every step logged as
   `[e1000e] step <name>: <result>` and kept for `/proc/net/nic` `init_*`):
   * `ulp_exit` (PCH): gate automatic PHY config, then
     `e1000_disable_ulp_lpt_lp(force)`: with an ME, H2ME request + wait for
     FWSM.ULP_CFG_DONE to clear (ms logged, >1 s flagged as the firmware bug
     Linux warns about); without, LANPHYPC toggle (LCD power-cycle done
     time logged), CV_SMB_CTRL unforce, K1 re-enable, ULP_CONFIG1 clear +
     START, FEXTNVM7, PHY reset.
   * `phy_init` (PCH): `e1000_init_phy_workarounds_pchlan` — PHY id under
     SWFLAG; on failure force SMBus, then LANPHYPC toggle (unless the ME
     blocks it), then unforce SMBus; PHY reset unless blocked.
   * `phy_id` (MDIO slow mode + retry if unreadable; flags a non-I217-class id
     on a PCH part).
   * `reset_hw` (MAC + PHY reset; LAN_INIT_DONE / PHYRA; post-reset: host
     wake-up bit, NVM LCD extended config when FEXTNVM.SW_CONFIG, OEM bits —
     says loudly if the platform disabled gigabit).
   * `nvm`: valid bank, checksum (0xBABA), NVM MAC, K1 word.
   * `k1`: Kumeran K1 state + PHY HV_PM_CTRL.
   * `reset` (`e1000e_reset`): PBA, FEXTNVM11 MULR fix, the SPT+ descriptor
     ring flush (on resets after the first), MAC+PHY reset, DRV_LOAD (tells
     the ME the driver owns the NIC), init_hw bits (TARC, ECC, MEHE...),
     RAR0, MTA, copper link setup (CRS on TX, downshift, auto MDI-X,
     10/100/1000 + pause advertisement, autoneg restart), FC timers and
     watermarks, TXDCTL, GCR, EEE advertisement (off by default).
   * `rings`: standard-frame receive workaround (`lv_jumbo_workaround(false)`,
     with the RX gate always released), TX (SPT IOSFPC/TARC0 errata), RX
     (legacy descriptors, SECRC, broadcast + all multicast), IMS.
3. **monitor** every 250 ms: MAC STATUS. Link up -> per-speed PCH work
   (ME DMoff exit, TIPG, EMI RX config, PLL clock gate, K1 clock request,
   SPT pointer gap at 1000, FEXTNVM4/6, LTR, EEE LPI), flow control from
   ADV/LPA, TCTL.EN, then `LINK_GEN` bump (the net server restarts DHCP).
   Re-runs that on a speed change or a link-change interrupt; link down ->
   FEXTNVM4/6 + LTR off. Without link: full MAC + PHY register dump at
   10/30/120 s, and one line if the PHY reports link but STATUS.LU does not.
   TX watchdog (5 s stuck -> ring flush + reset), RX watchdog (no frame
   consumed for 2 s while missed/no-buffer counters rise: kick, then re-arm
   RDT/IMS, then reset), ECC error interrupt -> reset, 30 s stats line.
4. **data path**: as r8169 (netdev `poll_receive`/`send_packet`, MSI
   NAPI-style: handler masks all (IMC) and acks what it read (ICR W1C),
   daemon re-enables IMS and re-checks the ring).

PHY register access holds EXTCNF_CTRL.SWFLAG (the ME arbitration flag) for
every MDIC sequence; failures are counted (`swflag_failures`) and logged.

### Kernel command line

`e1000e.disable=1`, `e1000e.msi=0` (polled), `e1000e.rxirq=0`, `e1000e.eee=1`
(advertise EEE; default off), `e1000e.speed=100`, `e1000e.k1=0` (force K1 off),
`e1000e.ulp=0` (skip ULP exit, diagnosis only), `e1000e.debug=1`.

## What only the laptop can prove

Everything PCH: the ME handshake (H2ME/ULP_CFG_DONE), SWFLAG arbitration with
a live ME, PHY page access (pages 769/770/772/776/779 at address 1), the
LANPHYPC/SMBus fallbacks, NVM flash reads, LCD extended config, K1/LTR/EEE
programming, the SPT ring flush, link on a real PHY, MSI on the PCH function,
throughput. Also: legacy RX descriptors (Linux uses extended ones on I219;
the hardware supports both, but this exact combination is untested there).

### Decision tree

- **No `[e1000e] found`**: compare the `[PCI] Found dev` lines; a 8086 id
  not in the table (I217/I218 or a newer I219) — send it.
- **`STATUS reads all-ones`**: function in D3cold / disabled in firmware
  setup ("Onboard LAN", "LAN PXE"); cold boot.
- **`step ulp_exit: ME path: FAIL ...`**: the ME did not release ULP within
  2.5 s. Retry with `e1000e.ulp=0` to see whether the PHY answers anyway;
  report FWSM/H2ME.
- **`PHY not accessible`** on every attempt (`step phy_init: FAIL`):
  SMBus/LANPHYPC recovery failed; `LANPHYPC toggle blocked by ME` means
  FWSM.RSPCIPHY is clear (an AMT SOL/IDE-R session or the ME still
  configuring). Power off fully (pull AC), boot again.
- **`SWFLAG not granted` / `swflag_failures` > 0**: the ME holds the PHY;
  report the EXTCNF_CTRL/FWSM values in those lines.
- **`(GIGABIT DISABLED by platform)`** in the OEM bits: BIOS power policy;
  link will be 100 Mb/s at most.
- **No link after 10 s** (`no link after 10 s: ... | PHY BMCR=.. BMSR=..`):
  BMSR bit 2 = link, LPA 0000 = partner never heard (cable/port). `PHY
  reports link ... but MAC STATUS.LU is 0` = MAC/PHY interconnect issue
  (Kumeran/SMBus) — report. Try `e1000e.speed=100`, `e1000e.k1=0`.
- **Link up, no DHCP**: `/proc/net/nic` `hw_stats`: rx_good rising but
  driver `rx_packets` 0 = RX DMA (descriptors/IOMMU); tx_packets rising but
  hw tx_good 0 = TX DMA (TX timeout lines follow). `rx_no_buf`/`rx_missed`
  rising = ring not refilled (RX stall lines).
- **Works, then stalls**: `TX timeout`, `RX stall`, `ECC error` lines and
  the 30 s stats; `e1000e.k1=0` and `e1000e.msi=0` are the first knobs.

## Review

A Linux-vs-driver audit of the PCH path (second pass) found no bring-up
blocker; it found four defects, all fixed before the final build: the
ring-flush dummy descriptor left its address in a live TX slot; FEXTNVM11
MULR fix was not set on the first reset; an error inside the receive-path
workaround could leave the PHY RX gate closed; the reset path held the ring
spin lock across sleeping PHY work. Also added from it: ECC error interrupt
-> reset, re-running the link-up work on renegotiation, skipping (with a log
line) NVM LCD-config entries on PHY pages the driver cannot address.

## Refuted premises / notes

- None of the PCH behaviour could be checked in QEMU; the 82574L shares only
  the MAC core. In QEMU the 82574's MDIO ownership bit does not latch, so the
  driver treats SWFLAG as best-effort on the 82574 (never on PCH parts).
- The disk was full (0 GB free) during this lane for about an hour; the
  first QEMU verification used a release kernel built with the
  `m7z2-kernel-only.sh` recipe on APFS clones of main's root images, the
  final evidence comes from a full `build-all.sh`.

  from real `build-all.sh` images.

  exercised in QEMU (no way to trigger it).
- QEMU's 82574 does not latch EXTCNF_CTRL MDIO ownership; SWFLAG is
  best-effort on the 82574 only.
