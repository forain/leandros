# lane/i915 — 2026-10-11 — Intel UHD 620 (Kaby Lake-R, 8086:5917): probe, execlist bring-up, UAPI foundation

Branch `lane/i915` from main `571ce20`. Not pushed, not merged. Target: the
i5-8350U laptop (Gen9.5 GT2, Sunrise Point-LP, eDP), booted from a USB stick
via UEFI + Limine with only the GOP framebuffer. End goal: Mesa iris (GL/GLES)
and ANV (Vulkan) on an i915-compatible kernel UAPI, KMS on the eDP, COSMIC on
the GPU (the GPU-only rule: init refuses the graphical login without a
hardware GL_RENDERER).

**Nothing here has run on Intel hardware yet. QEMU cannot emulate an Intel
GPU.** What QEMU proves: both arches build and boot to a shell with the code
in, the driver is silent without the hardware, and the whole bring-up path
(including the hang detector, state dump and engine reset) runs to completion
and returns in under 200 ms against fake registers (`i915.fake=1`).

## 3. Command line

Probe only is the default. Everything that touches an engine is opt-in.

| option | effect |
|---|---|
| (none) | G0 probe, ~0.5 s (GGTT scan bounded at 400 ms); engines untouched |
| `i915.off=1` | nothing at all |
| `i915.probe=0` | skip the probe's logging (bring-up still runs if asked) |
| `i915.ggttscan=0` | skip the GGTT occupancy scan |
| `i915.dumpvbt=0` | no base64 VBT in the log (default on, ~11 KB of log) |
| `i915.selftest=LIST` | comma list of `store`, `blt`, `fb`, `rcs`, or `all` |
| `i915.start=1` | bring-up + `store` (until the UAPI backend exists) |
| `i915.reset=0` | skip the GT reset before the bring-up |
| `i915.timeout_ms=N` | per-request budget (default 500; stall limit = half) |
| `i915.selftest_hold_ms=N` | how long the fb bars stay before boot continues (1500) |
| `i915.ggttbase=0x..` | GGTT window for kernel objects (default: top 16 MiB) |
| `i915.fake=1` | testing: bring-up against RAM posing as registers (QEMU), then the G3 UAPI with the soft engine |
| `i915.fake=2` | testing: the fake device's G3 UAPI only (what `i915test` / `gpuprobe gl` run against in QEMU) |
| `i915.uapi=1` | real hardware: register the G3 node (card0/renderD128 say `i915`); EXECBUFFER2 -> ENODEV until G3b. With `i915.fake`, `i915.uapi=0` keeps the node off |
| `i915.uapi_log=N` | 0 silent, 1 errors (default), 2 every ioctl to klog, 3 every ioctl to the console |

## 4. First laptop boots — what to run and what to grep

Stick: `LEANDROS_USB_EXTRA_CMDLINE="..." ./scripts/write-usb.sh x86_64 /dev/diskN`,
or edit the `cmdline:` line of `limine.conf` on the stick's EFI partition.
Log: `scripts/read-usb-log.sh`, then `grep '\[i915\]'`.

**Boot 1 — default (probe only).** Expected, in order:
- `identified: Kaby Lake GT2 Mobile (KBL-R ULT, UHD Graphics 620) ... the target laptop's UHD Graphics 620`
- `BAR0: mem64 non-prefetchable ... size=16 MiB (GTTMMADR ...)`, `BAR2: mem64 prefetchable ... 256 MiB (GMADR ...)`
- `GGC=0x....: GGTT 4 GiB ... stolen 32/64 MiB at 0x...` — note the stolen size and base
- `boot framebuffer phys 0x... = GMADR+0x... -> GGTT offset 0x...` (expect offset 0 or small)
- `display power: ... PWR_WELL_CTL1(BIOS)=... [PW1=on PW2=...]`
- `transcoder eDP: ENABLED ... DDI A DP-SST x2|x4 ...; active 1920x1080 ...` and `GOP scanout: eDP fed by pipe A`
- `pipe A plane 1: ENABLED XRGB8888 Linear ... surface GGTT 0x... == boot framebuffer GGTT offset (OK)` — **a MISMATCH here means the fb self-test will skip itself**
- `pipe A: ... frame counter N -> N+2 or +3 in 40 ms (scanning out)`
- `GGTT: boot framebuffer [...]: ... N/N present, contiguous=1, all in stolen ...=1`
- `OpRegion at 0x...: version 2.x ...`, `VBT "$VBT KABYLAKE..." ... panel_type=...`, `VBT blocks: ...`, then a `-----BEGIN VBT-----` block (decode offline with `base64 -d | intel_vbt_decode --file=/dev/stdin` from igt-gpu-tools)
- `forcewake: acked in gt=.. us render=.. us media=.. us` — **if a domain does not ack, stop and report; nothing GT-side will work**
- `topology: ... slices=0x1 subslices=0x7 (3 total) EUs=24 (8/subslice ...)`
- `CS timestamp: ... -> 12000000 Hz; measured ~12000000 Hz` (the two must agree; Mesa needs this number)
- `GT frequency: ... RP0 1100 MHz ...`
- per-engine lines `rcs0/bcs0/vcs0/vecs0: MODE=... (execlists=0) ...` — expected all idle, legacy mode
- `GGTT scan: ... present in N run(s)` and the first runs
- `=== i915 probe done in N ms (no engine touched) ===`

**Boot 2 — `i915.selftest=store,blt`.** Expected:
`GT reset (GRDOM_FULL): done in N us`, `private PAT programmed: 0x3b2b1b0b00030907`,
`bcs0: execlists enabled: MODE=0x00008000-ish (run-list=1)`,
`self-test store/bcs0: request 1 completed in N us`, `CSB[..] status=... (idle->active ...)`,
`... = 0xc0ffee01 ... PASS`, `bcs0: context image saved by the GPU: RING_HEAD=0x..`,
`self-test blt: square 0 of 4096 pixels wrong, border 0 ... PASS`,
`=== i915 bring-up PASSED ===`. On a hang: the `hang:` line, `faults:` line and
the klog-only `ring[..]` / `context regs[..]` dumps are the evidence; the boot
continues after the engine reset.

**Boot 3 — `i915.selftest=all`.** Adds eight colour bars across the top of
the screen (held 1.5 s; photograph them), `bar centres read back through the
aperture: ff0000 00ff00 0000ff ... PASS`, then `self-test store/rcs0: ... PASS`.

Only the laptop can prove: forcewake acks, that the GOP framebuffer really is
GGTT-mapped stolen memory scanned out by the plane we think, the CS timestamp
rate, that execlists/LRC images/ELSP order/CSB layout are right, that the
blitter reaches the scanout (and through which GTT), coherency of the status
page and scratch writes, RCS context restore-inhibit without the golden
render state, and the reset path on real hangs.

## 6. G3 — what exists and the plan

`uapi_abi.rs` answers, without kernel state: GETPARAM for every id iris/ANV
read (CHIPSET_ID, REVISION, topology masks, EU total, CS_TIMESTAMP_FREQUENCY,
MMAP_GTT_VERSION=4, softpin/no-reloc/handle-LUT/batch-first, context
isolation mask, fence array; PXP/HuC ENODEV); QUERY TOPOLOGY_INFO /
ENGINE_INFO / MEMORY_REGIONS (+ ENODEV for hwconfig/GuC/geometry) with
Linux's length protocol; EXECBUFFER2 checks (softpin only, canonical 48-bit
offsets, engine map or legacy ring selection, fence array); context
GETPARAM statics (GTT_SIZE = 2^48) and the engine-map decoder.

Remaining G3 work, in order (each step testable in isolation):
1. Backend skeleton registered through `gpu_uapi` only after a passing
   bring-up (`i915.start=1`): VERSION "i915" 1.6.0, sysfs PCI identity
   (8086:5917, so libdrm/Mesa's loader picks iris), GETPARAM, QUERY,
   GET_APERTURE, GET_RESET_STATS, REG_READ (RCS timestamp 0x2358, iris'
   `iris_get_timestamp`).
2. GEM: CREATE/CREATE_EXT (memory-regions extension; system memory only),
   GEM_CLOSE, MMAP_OFFSET (WB/WC; one token per object), legacy MMAP,
   SET_DOMAIN/SET_CACHING/GET_CACHING (LLC-coherent; UC for scanout),
   MADVISE, SET/GET_TILING (metadata), BUSY/WAIT, USERPTR (EINVAL first).
   Open question: physically contiguous objects (what the gpu_uapi mmap seam
   supports today) vs page lists — large textures need page lists, as NVK's
   VRAM did not; plan a scattered-page mmap token.
3. VMs and contexts: VM_CREATE/DESTROY = one 4-level `hw::Ppgtt` per VM;
   CONTEXT_CREATE_EXT with SETPARAM (VM, ENGINES, RECOVERABLE, PRIORITY),
   per-(context, engine) LRC image + ring; render contexts need the gen9
   golden state (Linux `intel_renderstate` null batch), the KBL context
   workarounds (LRIs emitted at context init) and the GT/engine workaround
   registers from intel_workarounds.c, plus MOCS and L3CC tables and RPCS.
4. EXECBUFFER2: bind every softpinned object into the context's PPGTT, wait
   in-fences (syncobj via the existing `syncobj_core`), emit invalidate +
   MI_BATCH_BUFFER_START (PPGTT) + breadcrumb into the context ring, ELSP,
   out-fences = `EXT_FENCE` ids answered by a status-page seqno read; a
   watchdog thread built on `HangCheck` marks hung contexts (Linux: banned,
   GET_RESET_STATS counts) and resets the engine. Interrupts (MSI, GT IIR
   user-interrupt bits) replace polling.
5. PRIME export/import for cosmic-comp, then `gputest`-style autotest and
   glmark-like timing.
6. G4 KMS: take over the GOP-left pipe/plane: bind scanout BOs into the GGTT,
   flip by writing PLANE_SURF (+ stride/format for linear/X-tiled) on vblank;
   full modeset (DPLL, DDI training on eDP, PPS, backlight) only later.

## 7. Risks and decisions

- **GTT used by blitter commands in the ring** is not certain (PPGTT vs GGTT);
  the self-test mirrors every address identically in both so either works.
  Scanout pages are mirrored uncached (the display does not snoop the LLC).
- **RCS without golden state/workarounds**: the `rcs` store test uses only
  MI and PIPE_CONTROL; real 3D needs step 3 above.
- **The probe runs on every boot of an Intel GPU** (~0.5 s); writes only the
  forcewake request. `i915.off=1` disables it.
- **Environment**: during this lane the Mac's data disk hit 100% (another
  lane's or Docker's usage; ~125 MB free at worst), so `build-all.sh` could
  not finish here. QEMU verification used this branch's release kernels
  (built with build-all.sh's exact cargo flags + the stack-frame check) in
  small private boot images with the shared initrd/Limine and the shared
  f2fs data images under `-snapshot`. A full `build-all.sh` run is still
  owed before merge. Docker Desktop stopped starting after the Mesa
  container crash.

  (keep the GOP's watermarks on the native plane).

### lane/kmsflicker (2026-10-12, from `lane/laptop` b15413d) — boot-6 greeter/desktop flicker, cursor blinks

Boot 6 (`i915.uapi=1 i915.exec=1 i915.kms=1`): greeter + desktop usable but
flicker with render glitches, the (software-composited: no cursor plane is
advertised while gpu_kms is active) cursor blinks. The log has only
`kms: first flip` and NO `not latched` line, DC_STATE_EN=0. Reviewed against
Linux and found sound: SURF written last; flip waits SURFLIVE, so the DRM
event (100 Hz tick, after `present` returns) never frees a still-scanned
buffer; RMFB of the on-screen fb restores the GOP surface first; PRIME import
shares the obj so implicit sync (`last_fence`) holds; the rcs fini breadcrumb
is Linux's (RT/depth/DC flush + CS stall, then the post-sync write).
Remaining suspects, none provable from boot 6, so boot 7 measures them:
1. eDP PSR left on by the GOP (VBT has a PSR block; never read before):
   the panel would keep a self-refresh frame -> stale frames / cursor
   gaps. Now dumped at init and DISABLED by default (`i915.kms_psr=1` keeps).
2. Coherency: objects are LLC-cached in the PPGTT and the flip clflushes.
   Now (default `i915.kms_uncached=1`) an ADDFB'd object is rebound
   uncached (PPAT 3) in every PPGTT, Linux's I915_CACHE_NONE for scanout;
   the clflush stays. Only effective where Mesa uses the PTE MOCS
   (external BOs); `i915.kms_uncached=0` reverts.
3. FIFO underruns (GOP watermarks / SAGV under GPU load): `i915.kmsdebug=1`
   unmasks pipe A underrun in DE IMR (IER untouched) and counts it per flip;
   init line dumps PLANE_WM/BUF_CFG.
4. Console restores mid-session (flip to the GOP surface and back): kmsdebug
   flip lines carry console-restores + VT-repaint counters and always log a
   flip whose prev fb is 0.
Linux 7.2.9 on the same laptop (debugfs): panel has NO PSR, FBC disabled,
pipe A 1920x1080 native without scaler, primary XB30 Y-tiled, and a HW
cursor plane (cursor A AR24 64x64). PSR/FBC are therefore unlikely; both
are still logged and, if found enabled, turned off (`i915.kms_psr=1` /
`i915.kms_fbc=1` keep). Our card0 does NOT advertise a cursor plane while
gpu_kms is active (GETPLANERESOURCES lists the primary only, atomic
rejects cursor props) — cosmic-comp composites the cursor, so a
half-implemented cursor plane is ruled out. A real CUR_CTL/CUR_BASE/CUR_POS
cursor (pinned uncached 64x64 ARGB, CUR_BASE last) is a later step.
Boot 7 cmdline adds `i915.kmsdebug=1`; grep `kms:` (`eDP PSR_CTL`, `flip #`,
`underruns`, `NOT LATCHED`, `RMFB of the on-screen`). If underruns climb:
watermarks/SAGV next (pcode SAGV disable). If flicker persists with zero
underruns/restores and PSR off: compare `kms_uncached=0/1`.

### G4a state (2026-10-12, branch `lane/g4` from `lane/laptop` 2983858) — KMS + iris desktop path, UNTESTED ON HW

- Boot-3 `faulting_batch_in_reset_stats: FAIL` root cause: the test stored to an
  unbound PPGTT address. On gen9 hardware that is not a hang — the write is dropped
  and the batch completes (Linux behaves the same; no reset, active=0). Only the
  soft engine treated it as a fault. Fixed in the test (`c5beef8`): the batch now
  jumps to itself (a real hang: hangcheck stall 3 s, or the 20 s budget if ACTHD
  keeps moving) and the test waits on it (up to 30 s) before GET_RESET_STATS. On
  the laptop expect an `rcs0: request N of context ... HUNG|TIMED OUT` line and an
  engine reset during i915test; i915test takes 3-20 s longer.
- `drivers/src/i915/kms.rs` (`606fe31`), only with `i915.kms=1`, on hardware only
  when exec is ready and plane 1A / PIPESRC / SURF match the GOP framebuffer:
  registers a `gpu_kms` backend ("i915-plane"). Mode = the GOP mode (1024x768 on
  the laptop; the GOP's pipe scaler stretches it to the 1920x1080 panel — no
  modeset, no native mode yet). ADDFB/ADDFB2 (LINEAR XR24/AR24, pitch %64, fb >=
  mode) takes an export ref on the i915 object and binds it into a 16 x 32 MiB GGTT
  window at 1 GiB. Present = wait the object's last fence (1 s), clflush the
  scanned rows (display does not snoop LLC; all objects are LLC-cached), write
  PLANE_CTL(linear RGB8888)/STRIDE/OFFSET, then PLANE_SURF; wait up to 50 ms for
  PLANE_SURFLIVE (logs `kms: flip ... not latched` if not). Events = the DRM
  layer's 100 Hz synthetic vblank, as on NVIDIA.
- `gpu_kms::KmsBackend` gained `console_restore` (lock-free): called when the
  scanout goes back to the console (card0 release, VT revoke, panic, stale present)
  so the plane points at the GOP surface again. NVIDIA passes `None`.
- `gpu-env`: iris branch for `card0=i915`, requires ` i915.kms=1 ` in
  /proc/cmdline, pins VK_ICD to intel_icd if present, path name `iris`, clients use
  wgpu GLES (`WGPU_BACKEND=gl`) like virgl.
- Build: `INTEL=1 ./scripts/build-all.sh` (or `LEANDROS_GPU_INTEL=1`) ships
  `gpu-stage-x86_64-intel` (iris + ANV) instead of the shared x86_64 stage.
  `LEANDROS_GPU_STAGE` still overrides both. The laptop stick MUST be an INTEL=1
  build (otherwise gpuprobe has no iris and the login is refused).
- QEMU (release, INTEL=1 build): default x86_64 and aarch64 boot, `ls /dev/dri`
  RC=0, zero `[i915]` lines on x86_64. `i915.fake=2 i915.kms=1`: i915test
  failures=0 on both arches (incl. kms_addfb2_linear / kms_addfb2_xtiled_einval /
  kms_rmfb and the new hang test); on x86_64 the whole greeter chain ran on the
  fake device: `gpu-env: renderer=iris GL_RENDERER='Mesa Intel(R) UHD Graphics 620
  (KBL GT2)'`, `gpu-env: iris GLES 3.2 wgpu=1`, cosmic-greeter started and
  `kms: first flip: fb 1 (1920x1080 pitch 7680)` (soft engine: no real pixels).

BOOT-4 kernel command line (laptop; keep the boot-3 line's non-i915 options, e.g.
the Wi-Fi ones, unchanged and replace its i915 options with):
  `i915.uapi=1 i915.exec=1 i915.kms=1`
Expect: G3b exec lines as in boot 3, then `==== G4a KMS registered: card0 scans out
1024x768 on pipe A plane 1A ...`; greetd's log shows `gpu-env: renderer=iris`; the
kernel log `kms: first flip: fb N (1024x768 pitch 4096) at GGTT 0x4000xxxx`. If the
greeter screen is garbage/stale: coherency (clflush) — try making scanout objects
UC in the PPGTT; if `not latched`: the plane is not updating (check PLANE_SURFLIVE
/ pipe vblank). `i915test -v` on a VT should now end with `failures = 0` (incl. the 3 kms checks).

Risks / not done: no native 1920x1080 (needs PIPESRC + scaler + plane size, and
the console restore must undo it); no X-tiled/Y-tiled/CCS scanout (iris may
render to LINEAR slower); flips wait synchronously (≤ one frame) in the ioctl;
clflush of ~3 MiB per frame; no real vblank IRQ/timestamps; KMS on a fb pitch
other than the GOP's keeps the GOP's watermarks/DDB (a pitch change could
underrun); i915 handles are dense from 1 and the DRM layer's dumb/blob handles

  OUT sync_file fds -> EINVAL), REG_READ (RCS timestamp only), GET_RESET_STATS,

- Model: objects = one zeroed buddy block each (contiguous, power-of-two,
  max 1 GiB); every VM = a real 4-level `hw::Ppgtt` (KStore pages) +
  `vmbind::VmMap` (Linux softpin move/evict rules); each open has context 0
  with its own VM; GETPARAM(VM) mints a new id (iris's global VM). Fence id =
  `EXT_FENCE | engine<<48 | seqno`; `fence_done` compares with an atomic
  per-engine COMPLETED. Dead objects are unbound from every VM before their
  pages go back (zombie list while a fence is pending).
- GEM handles are dense per open from 1 (Linux idr). **Lesson:** the NVK
  layer's 0x4000_0000 handle base makes iris memset a 4 GiB
  `index_for_handle` array at its first flush -> OOM/SEGV in gpuprobe.
- Fake engine (`i915.fake=1|2`): `softcs` runs the batch synchronously through
  the context's page tables: SDI, SRM (RCS timestamp), MI_COPY_MEM_MEM,
  PIPE_CONTROL post-sync writes, BBS chaining + 2nd level; everything else
  skipped by length. A fault/bad command/runaway counts as a hang
  (GET_RESET_STATS batch_active, ban if non-recoverable). iris's real init
  batches (95 and 74 dwords) walk to MI_BATCH_BUFFER_END cleanly.
- `/bin/i915test` (userland/i915test, relibc-linked): 50 assertions, all PASS

Known limits / risks of the G3 code:
- All CPU mappings are write-back and all PPGTT PTEs are `Cache::Cached`
  (LLC-coherent). A WC/UC MMAP_OFFSET request gets WB; MOCS entries that
  bypass the LLC could then read stale data on hardware — revisit with G3b.
- Freeing an object that userspace still has mmapped returns its pages
  (same as the NVK layer); Mesa unmaps before GEM_CLOSE.
- The DRM layer's GEM_CLOSE of an unknown handle answers 0 (Linux: EINVAL).
- Contiguous power-of-two objects waste up to 2x and fragment; a scattered
  page list needs a page-list mmap seam in `gpu_uapi`.
