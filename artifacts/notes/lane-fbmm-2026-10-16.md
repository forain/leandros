# Lane fbmm — 2026-10-16

Branch `lane/fbmm` off local main `aac2e1e0`. Not pushed.

## The fact

HP EliteBook 840 G5 (i5-8350U, UEFI, Limine from the USB stick). With BIOS
**Fast Boot OFF** the kernel paints only stage square 1 (white, "kernel
entered", lane rebootq) and freezes; square 2 ("memory manager up") never
appears. Fast Boot ON boots fine. Nothing reaches the stick log.

So it stops between `early_mark(1)` and `early_mark(2)` in
`kernel/src/main.rs::kernel_main`: `boot::limine::parse_with_requests`, then
`mm::init_with_map` = `buddy::init_from_map` (free-head bitmap carve + a
free-list header written into the first 24 bytes of every free block, all
RAM, through the HHDM) → `buddy::init_site_tags` (alloc + zero ~4 MiB) →
`slab::init` (alloc + zero ~9 MiB) → `atomic_pool::init`.

## Audit of that window (what a different map could break)

| item | before | risk | now |
|---|---|---|---|
| Limine parser cap | first **256** entries, rest dropped silently | lost RAM (highest addresses first), not a hang | 1024 kept, count reported (`[MEMMAP] sanitize: reported N kept M`) |
| sort / overlap / zero-length / wrap | passed straight to the buddy | an overlapped "usable" range that is really NVS/reserved gets free-list headers written into it (firmware memory corruption → SMI handler / runtime crash = freeze); `base+length` wrap → garbage bounds | `boot/src/memmap.rs::sanitize`: sorted, non-overlapping, most-restrictive kind wins, merged, usable page-aligned inward, clipped at 2^46, nothing wraps |
| buddy region bounds | `(base + length) as usize` | overflow on a wrapping entry | saturating (`region_end`/`region_start`) |
| free-head bitmap placement | FIRST usable region >= 1 MiB that fits (0x100000 on the HP) | the lowest megabytes are where firmware leftovers sit | top-down (highest region that fits, like Linux memblock); steps below reserved ranges |
| `RESERVED` table | 8 slots, overflow silently ignored | a dropped reservation = kernel/initrd handed out (direct boot) | 32 slots, overflow logged |
| HHDM coverage | buddy writes only to usable ranges | Limine maps every usable entry in the HHDM in all base revisions; not a credible cause | unchanged (the early IDT now shows a #PF if it ever happens) |
| panic in the window | `loop {}` after serial prints (no UART on the laptop) | **invisible freeze** — e.g. the buddy's own `CORRUPT LINK` check (`report_bad_link` → `panic!`) fires if anything else writes into a free block | panic message + location painted on screen (red bar top-right), knob or not |
| CPU exception in the window | vectors through the firmware's IDT (left loaded by Limine; its handlers live in boot-services memory we are handing out, maybe not even mapped) | **invisible freeze** (firmware dead-loop) or triple-fault reset | `arch/x86_64/src/early_idt.rs`: vector/err/RIP/CR2/CR3/regs + last stage painted (magenta bar), halt; NMIs reported and resumed |

Fast-Boot-ON map of the HP (klog 2026-10-16 07:07): 50 Limine entries, all
sorted, disjoint, page-aligned; usable top 0x43F800000 (17 GiB span, 15.6 GiB
usable); kernel+modules at 0xC00000 (+0x422000); bitmap would be 544 KiB. No
limit in the old code is anywhere near this map. A full-init map adds entries
(more boot-services/runtime/reserved fragments, USB legacy buffers) but
Limine sanitizes and merges, so overflowing 256 is unlikely on this machine.

## Root cause — ranked (not proven on hardware yet)

1. **A fatal event in the window that was invisible by construction.** Every
   failure path between square 1 and square 2 ended silently (panic →
   `loop {}`; exception → firmware IDT). That is fixed outright: the next
   photo will show which of these it is.
   Within it, the most plausible Fast-Boot-OFF-only trigger: **firmware still
   using memory Limine reports as usable**. Fast Boot OFF = full USB
   enumeration + legacy USB emulation (SMM) live until our stage-10 BIOS
   handoff. This kernel writes into the first bytes of EVERY free block across
   all RAM at stage 2 (intrusive free lists), Linux does not (struct-page
   metadata) and runs its handoff in early PCI quirks. A DMA/SMM writer in
   "usable" RAM would either trip the buddy's link check (now: red panic text
   "buddy free list corrupt" with node/value on screen via the tee) or crash
   SMM (freeze with the last `[mm] free #k base-end` line on screen —
   then bisect with `mm.reserve=`).
2. A CPU exception (NMI/#MC/#PF) taken in the window — now shown.
3. A map shape the old code mishandled (overlap/unsorted/wrap/>256) — fixed
   by the sanitizer whatever the photo shows.

## Knobs (kernel command line)

| knob | meaning |
|---|---|
| `earlyfb.memmap=1` | before mm init: Limine's raw map (index, base, length, type; 3 columns at 1920 px, 2 at 1024 px), kernel/module/fb addresses, sanitizer stats; then every early serial line on screen (mm progress `[mm] free #k ...`, everything up to the console) |
| `earlyfb.log=1` | only the serial tee (no map table) |
| `earlyfb.pause=S` | hold S seconds after the map dump and again after stage 2 (TSC rate from CPUID) |
| `earlyfb.stop=N` | halt on purpose right after stage N's square (photo without time pressure) |
| `earlyfb.scale=1..4` | font scale (default 2; drops to 1 automatically when the map would not fit) |
| `earlyfb.test=panic\|fault\|nmi` | provoke the early fatal path once, to see it |
| `mm.reserve=0xS-0xE[,...]` | keep physical ranges out of the buddy (bisect "firmware still uses this RAM") |
| `memmap.fragtest=N` | test: rewrite the boot map into a reversed, overlapping, N-holes-punched one before sanitizing (QEMU reproduction) |
| `earlyfb=0` | everything off (existing) |

Panic/exception text needs no knob.

## For the user (laptop, Fast Boot OFF)

1. Boot the trial slot with `earlyfb.memmap=1 earlyfb.pause=15` added.
   Photograph the WHOLE screen as soon as the table appears (the map), and
   again when it stops changing (the last lines).
   - red bar top-right + "KERNEL PANIC" → photo the message/location;
   - magenta bar + "CPU EXCEPTION" → photo vector/RIP/CR2;
   - neither, text frozen → the last `[mm] ...` line names the step/region;
   - green "[early] stage 2: memory manager up" → mm is fine, the boot gets
     further (squares 3+ and log lines continue).
2. If it froze inside `[mm] free #k A-B`: retry with `mm.reserve=A-B`.
3. Compare the photographed map with the Fast-Boot-ON one above.

Note: `earlyfb.log=1` also draws the map table (both set the same verbose
flag); `earlyfb.memmap=1` additionally picks the largest scale at which the
whole table fits.

## Tests

Host:
- `cd boot/memmap-tests && cargo test` — 6 tests (debug and release): the
  HP Fast-Boot-ON map is preserved exactly; 25 seeds x {64, 300, 400, 1024}
  entries of unsorted, overlapping, duplicated, zero-length, unaligned,
  wrapping, up-to-72-GiB maps checked against an independent reference
  (no byte reported usable that any input calls non-usable; usable byte
  count exact); output-buffer overflow is counted, not fatal.
- `cd mm/buddy-tests && cargo test --release` — the real buddy.rs over an
  80 GiB lazily committed host span, fed a sanitized 401-entry hostile map
  (-> 442 entries, 155 conflicting overlaps): page count exact, full drain
  never returns a non-usable / sub-1MiB / overlapping block, full refill
  re-merges to a 1 GiB block, 0 bad frees.

QEMU (release, both arches):
- default boot: `[MEMMAP] sanitize: reported 37 kept 37 -> 28 entries`
  (x86_64; adjacent reserved merged, nothing else changed); buddy page
  total identical in kind to before.
- `memmap.fragtest=600`: x86_64 640 -> 1231 entries, aarch64 629 -> 1221,
  601 conflicting overlaps, unsorted, wrap 1, zero 1; both boot to login
  and run commands.
- regress suite: aarch64 PASS 24/24, x86_64 PASS 24/24.
- screenshots in `artifacts/notes/fbmm/`: `x86-memmap.png`
  (`earlyfb.memmap=1 earlyfb.stop=2`, 1920x1080), `x86-1024.png` (same at
  1024x768), `x86-panic.png` (`earlyfb.test=panic`), `x86-fault.png`
  (`earlyfb.test=fault`: #PF, CR2 0x100000000000), `x86-nmi.png` (NMI
  reported, boot continued to stage 2).

QEMU places the Limine kernel at phys 0x77fc4000; the HP at 0xC00000. Both
fine.
