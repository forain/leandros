# RDD VA-API hang: A/B and lock identity (2026-10-19)

Laptop on trial `47756695bf0c` (`#1 main-66d64d1c`, `deploy-kernel --netwatch 180 --reboot`, **not promoted**; good is still
`6c5e004ed5cd`). Session via greetd IPC. Firefox on aqz-KE-bpKQ with the 3 VA-API prefs and `LIBVA_DRIVER_NAME=iHD`. Each launch was
measured over a 25.7 s window at ~75-100 s after launch. Script: scratchpad `rddab/ab.sh`.

## Root cause: self-deadlock on mozglue's `gEnvLock` (the libc build is at fault, not the kernel)
The hung thread is the same in both hangs:
`MediaSupervisor #1  futex  fut=0x26bb24 fval=0x80000010 rip=0x300a4d6b`
- `fut`: the `firefox` executable is PIE, loaded at 0x200000. `gEnvLock` is at firefox+0x6bb20, and musl's `_m_lock` is at +4, so
  firefox+0x6bb24 = 0x26bb24.
- `fval`: 0x80000010 is a musl normal mutex, locked (EBUSY=0x10) with the waiter bit set. musl does not record the owner tid.
- `rip`: `ld-musl`/`libc.so` loads at INTERP_BASE 0x30000000, so the rip is libc+0xa4d6b. That is the instruction right after
  `syscall` in `__syscall_cp_c`, the non-cancellable `__timedwait` used by `pthread_mutex_lock`. Every other RDD futex waiter
  (`fval=2`, rip `__cp_end`) is an ordinary condvar wait on its own stack.
- The mechanism, from the shipped `/usr/lib/libc.so` (musl 1.2.5, 4.3 MB):
  `setenv` at 0x59170 calls **`getenv@plt`** (at 0x5922e, on the `!overwrite` path), and libc.so has a `R_X86_64_JUMP_SLOT getenv`.
  So the sequence is: mozglue `setenv("LIBVA_MESSAGING_LEVEL", .., 0)` takes `gEnvLock`, then musl `setenv` (overwrite=0) calls
  `getenv` through the PLT. That resolves to Firefox's exported interposer `getenv`, which calls `pthread_mutex_lock(gEnvLock)`
  on the same thread and deadlocks. Upstream musl links libc.so with `--dynamic-list=dynamic.list`, so its internal `getenv` call
  binds locally. Our libc.so was linked without that list, which makes every internal libc call interposable.
- This explains why the hang is deterministic, and why the earlier success (log4) had both variables preset: no setenv ran.
  The kernel's futex code is not involved. Any mozglue process that calls `setenv(.., 0)` on an unset variable hangs the same way.
- `/proc/<pid>/maps` returned 0 bytes, even on a fresh RDD, so the mapping comes from ELF symbols plus the fixed load bases
  (no ASLR). smaps was not read.

## Fix (one lane)
**Port patch to the shipped musl `libc.so`:** relink it the way upstream musl does (`-Wl,--dynamic-list=dynamic.list`, or at least
`-Bsymbolic-functions`), so that libc-internal calls such as setenv calling getenv no longer go through the PLT. Check: `getenv` no
longer appears in `llvm-readelf -r libc.so`, then repeat launch A 3/3 without the env exports. The env workaround (exporting
`LIBVA_MESSAGING_LEVEL=0` in `ports/firefox/firefox.sh`) works, as B shows, but it covers only this one call site.
