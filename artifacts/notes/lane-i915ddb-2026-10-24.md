## What changed
- kms.rs `skl_ddb_plan` / `ddb_setup`: gen9 892 usable blocks (896 - 4 bypass). When pipe A is
  the only lit pipe and 1A its only enabled plane: plane 1A 0..860, cursor 860..892 (Linux:
  cursor max(32 with one pipe else 8, its min_ddb) at the pipe top, one plane takes the rest).
  Other pipes lit / other planes on / firmware 1A range reaching the cursor range -> firmware
  allocation kept. `i915.ddb=0` = old behaviour. PLANE_BUF_CFG is written right before the next
  PLANE_SURF (armed together with the WMs); the cursor range never moves, the plane only grows
  into unused blocks, so no overlap at any vblank.
- WMs: plane recomputed against 860 blocks; cursor gets its own skl_plane_wm(width 64, 32 blocks)
  (cursor.rs `set_wm`), both capped to the common level count as Linux does.
- /proc/i915: `ddb_plane`, `ddb_cursor` (raw BUF_CFG).
- GEM_MMAP (+I915_MMAP_WC) answered in kernel/src/syscall.rs: MMAP_OFFSET (WC/WB) in place on the
  caller's struct (restored), range check, mmap from the object start, head unmapped, addr_ptr set.
  Unknown flags EINVAL, past-object EINVAL (Linux semantics).
- MMAP_OFFSET_FIXED -> ENODEV: Linux `__assign_mmap_offset` returns -ENODEV for FIXED on every
  object without obj->ops->mmap_offset (only TTM/lmem objects on discrete parts have one).
