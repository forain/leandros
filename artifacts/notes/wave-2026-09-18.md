## Refuted premises (remove from TODO/memory)
- "RUN_QUEUE try_lock fails >50 % of ticks / there is a long holder" — 8.2 %, sub-µs holds.
- "brush wedges because a pipeline wait errors" — no wait errors on LeandrOS; it was `kill` vs `killpg`.
- "`kill_next_group_member` frees an off-CPU Blocked sibling's stack in place → corruption" — ownership is sound.
- "~140 MB of KERNEL memory leaks per compositor death" — mostly a userspace orphan; the kernel part was page tables + ownerless dumb buffers.
- "The aarch64 greeter frame rate under pointer motion measures the GPU path" — cursor-plane-only, input-bound.
- The pipe POLLOUT test, not the kernel, was wrong.

**`polltest poll_timeout_wake_latency` FAILs on both arches — not a lane regression.**
aarch64/HVF ×4: p50 9728–9944 µs, p90 10072–10145, p99 ≤ 11.2 ms, max ≤ 19 ms, early=0
(host load 2.8–5). x86_64/TCG: p50 9278, p90 10324, p99 11346. The signature is a
deterministic one-tick overshoot, not host noise or lock contention (`[RQPROF]`
tick failures 0.02 %). Bisect: a kernel built at `012e57a` (integ with only
timespec/tsccal/brush/vfsperm2/runq/pollout — before execfd, misc, complk, gpuirq)
reproduces it exactly (p50 9936/9945, p90 10012/10014), so none of execfd/complk/gpuirq is
guilty and nothing was reverted. Cause: lane/runq calibrated the bound (`p90 ≤ 5 ms`) on
tick-floored deadlines, where `poll(10 ms)` fires at the next tick edge (its table: p50 = 0);
lane/timespec (not in runq's ancestry) made every timed wait an absolute `monotonic_ns()`
deadline that is never early, and the wake is still tick-granular, so a back-to-back
`poll(10 ms)` loop re-arms just past a tick edge and is released one tick later — an
overshoot of 10 ms − ε every time. This is the "wake latency is tick-bounded (≤ 10 ms late)"
item already in the still-open list; the fix is a one-shot timer armed to
`NEXT_POLL_DEADLINE` (or a sub-tick-aware test bound). Carried into `TODO.md`.
