## Item 1 — x86_64 serial Ctrl-T (0x14) task-dump byte loss

**Root cause:** `sched::dump_tasks()` (the Ctrl-T SysRq-t equivalent) emitted every byte
through the ordinary `arch_serial_putc` → `putc()` path, which both arches share a single
sticky `TX_WEDGED` latch across: once any one byte's bounded deadline expires (a transient
stall while the socket-backed QEMU chardev on the other end catches up — not a genuinely dead
consumer), `TX_WEDGED` latches true and *every later byte, from any caller, until one probe
finds room again* takes a single-LSR-probe-and-drop fast path with **no wait at all**. A
kilobyte-class burst like the task dump is exactly the shape that turns one transient blip
into a dropped chunk the size of "however many bytes this loop emits before the host catches
up" — matching the reported ~1.5 KB hole in the middle of a dump.

**Fix:** added a separate blocking putc path used ONLY by the diagnostic dump, which never
reads or sets the shared `TX_WEDGED` latch and instead does a full per-byte bounded-deadline
poll of LSR.THRE (x86_64) / FR_TXFF (aarch64) every time. A transient stall now costs at most
one byte, not the rest of the dump, while still not risking a true indefinite IRQ-context
stall (same deadline bound as before, just evaluated fresh per byte).

- `arch/x86_64/src/lib.rs`: new `pub unsafe fn putc_dump(c: u8)`.
- `arch/aarch64/src/uart.rs`: new `pub unsafe fn putc_dump(c: u8)` (symmetric, PL011).
- `kernel/src/main.rs`: new `arch_serial_putc_dump` extern "C" wrapper dispatching per arch.
- `sched/src/lib.rs`: `dump_raw::{ph,pn}` and `dump_tasks()`'s `print_str` now call
  `arch_serial_putc_dump` instead of `arch_serial_putc`.

**Evidence (x86_64/KVM):** sent raw 0x14 five times over the serial socket in one boot
(`/tmp/ctrlt_test.py`, saved output). All 5 dumps: 31 `[TASKS]` lines + header + the
`buddy free_pages=... blocks/order: ...` census footer present and byte-identical across
runs (aside from the `tick=` counter). No truncation, no garbled mid-stream bytes.

**Not verified:** aarch64 (PL011 side of the fix builds — same file compiled cleanly as part
of the full aarch64 release build — but was not boot-tested; the reported bug was x86_64-only
so this is lower risk, but flag it as unverified).

## Item 2 — vfstest residue on re-run in the same boot

**Root cause, two independent spots:**
1. `test_chroot_confines_symlink_resolution` unconditionally `mkdir("/tmp/jail")`s in the
   forked child; a second run in the same boot hits EEXIST → `exit(1)` → reported FAIL, even
   though the actual jail-confinement behavior is fine. (The function's own comment already
   said "leaving /tmp/jail behind is fine" — true for reboots, false for same-boot re-runs.)
2. `test_xattr_list` recreates its file with `O_CREAT|O_WRONLY|O_TRUNC`, which — correctly,
   matching real xattr semantics — does NOT clear xattrs left on that inode by a previous run.
   Its "freshly created file lists 0 xattrs" assertion then fails on the second run because
   `user.a`/`user.b` are still there from the first.

**Fix:** both idempotent now. The jail test does a best-effort `unlink(link); rmdir(jail)`
before `mkdir` (harmless ENOENT on a first run). `test_xattr_list` does a best-effort
`unlink(path)` before reopening, forcing a genuinely fresh inode.

**Evidence (x86_64/KVM):** ran `vfstest` twice in one boot, no reboot between: 39/39 PASS
both times (was: `chroot_confines_symlink_resolution` and `xattr_list_tmpfs`/`xattr_list_f2fs`
FAIL on the 2nd run before this fix, per the bug report — not independently re-confirmed as
failing pre-fix in this session, took the report at face value and verified the fix holds).

**Not verified:** aarch64 (builds; not boot-tested this session).

## Item 3 — `/run/cosmic-greeter` not seeded

**Root cause:** `userland/init/src/main.rs::seed_runtime_dirs()` already walks `/etc/passwd`
at boot to create `/run/user/<uid>` for every non-root account (including the greeter's own
`/run/user/990`), but discarded the username field and never created upstream's separate
`/run/cosmic-greeter` runtime directory. Confirmed upstream's actual tmpfiles.d line via
`https://raw.githubusercontent.com/pop-os/cosmic-greeter/master/debian/cosmic-greeter.tmpfiles`:
`d /run/cosmic-greeter 0755 cosmic-greeter cosmic-greeter -`. cosmic-config's system-scope
store (linked into the greeter binary) targets that path; confirmed via `strings` on the
staged `cosmic-greeter-x86_64` binary that `/run/cosmic-greeter` is a literal it references.

**Fix:** `seed_runtime_dirs()` now keeps the username field and, when it equals
`cosmic-greeter`, additionally `mkdir`s `/run/cosmic-greeter` mode 0755 and `chown`s it to
that account's own uid:gid from /etc/passwd (990:990 in the staged image, not hardcoded).

**Evidence (x86_64/KVM):** `ls -ld /run/cosmic-greeter` after boot →
`drwxr-xr-x 1 cosmic-greeter cosmic-greeter ... /run/cosmic-greeter`. Did not separately
re-run the full greeter login flow to confirm the log complaint is gone (time-boxed) — the
directory now exists with correct mode/owner, which is the fix upstream's tmpfiles.d line
itself provides, so I'm confident but this specific log-line disappearance is unverified.
