# lane podl0 (2026-11-13)

## L0 rootful `--network=pasta -p`: REFUTED
Podman 5.8.9 refuses it as root: `invalid config provided: pasta networking is only supported for rootless mode or when inside a nested userns` (rc=125). This is a podman-side gate; we do not work around it. Guard `podman_pasta_root_rejected` in podbridgetest. Rootless `-p` works (podpastatest pasta_portfwd). Bridge `-p` still waits for nf_tables.

## `--internal`: FIXED (sched/src/ns.rs netctl_set)
Fail-first: `podman_internal_forwarding_kept` (internal network container up, `echo 1 > ip_forward`, read conf/<bridge>/forwarding) gave FWD=1 before the fix, FWD=0 after.
Linux semantics (devinet_sysctl_forward): ip_forward and conf/all/forwarding are the same variable; inet_forward_change fans out to all/default and every device ONLY if the value changed. We fanned out on every write. Now fan-out happens only when conf/all/forwarding changes. Per the netavark 1.17.2 nftables capture (designs/podnat-capture, scenario e) an internal network also gets `oifname "<br>" drop` isolation rules on Linux; those are nft-specific and not built here (firewall_driver=none), so forwarding=0 is the only isolation and this is the interim fix. A genuine 1->0->1 toggle still clobbers, as on Linux.
Test-harness: podbridgetest now runs `podman rm -af` first (a stale --rm container made podman_echo fail on reruns).
