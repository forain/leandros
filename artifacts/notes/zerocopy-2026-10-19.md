# Laptop 2026-10-19: where the CPU goes during YouTube playback, VA-API vs software (zerocopy)

Kernel good `d3c90702a894` (`#1 main-cfe62bbf`), rebooted for a fresh login and session started over greetd IPC at uptime ~45 s.
All windows ran with the panel `On` (`blanktest --status` before and after each one) and finished before uptime 900 s.
Video: aqz-KE-bpKQ. Each launch was measured over a 30.8 s window at +55..+85 s after RDD appeared.
Script: scratchpad `zc/m.sh`. Analysers: `zc/thr.py` (per thread, from `/proc/*/task/*/stat`) and `zc/sc.py` (per-syscall deltas
from two `/proc/sysstat` reads). Software decode was forced with `LIBVA_DRIVER_NAME=zcnone` in the launch env, so **no prefs were
changed** (user.js and prefs.js were not touched). Firefox was stopped at the end and `/tmp/gc` removed.

## 1. What YouTube serves: H.264, 854x480, 30 fps, in both modes
From MOZ_LOG (`PlatformDecoderModule:4,FFmpegVideo:4,Dmabuf:4`, separate launch `hwlog`):
- `FFmpegVideoDecoder MIME video/avc Codec ID 27`, and `RemoteDecoderChild ... ffmpeg video decoder (RDD remote), codec: h264`.
- `plane 0 size 854 x 480 format 20203852` (R8), `plane 1 size 427 x 240` (GR88), so NV12. `frame duration 33.33`.
- HW decode: `average decode time 0.56 ms`, 2510 frames, `VA-API Got one frame output`. The accelerated list is h264, vp8, vp9
  (vp9 profile 2 is not supported: `p010le`).
- SW run: RDD threads `av:h264:df0`/`df1` (system libavcodec h264 frame threads), 3.6 % each.
- 480p comes from YouTube auto-quality matching the default (non-theatre) player size, not from a decoder limit.

**Consequence: software decode of this stream costs only ~7 % of one core**, so VA-API can never save 40 % on this video.

## 2. Zero-copy: yes, end to end into WebRender
- RDD: `ImportPRIMESurfaceDescriptor() FOURCC NV12` per frame, `UpdateYUVData() copy 0` on all 2510 frames,
  `Surface pool ... used copied 0`. There is no vaGetImage, hwdownload or GL copy in RDD.
- Parent: the Compositor runs `ImportSurfaceDescriptor` with the plane fds. The Renderer runs `CreateEGLImage() plane N ... Success`
  and `CreateTexture` per plane per frame, then `ReleaseEGLImages`. So our i915 PRIME import plus iris EGLImage works
  (linear/modifier path, no failures).
- WebRender then draws the YUV texture into its own window buffer, and cosmic-comp composites that buffer. The video does not
  reach cosmic-comp as its own dmabuf subsurface (the native Wayland compositor is off), but nothing is read back to the CPU.
- The P5b 7.7 ms/frame hwdownload cost does not apply to Firefox.

### Why: broadcast-mask parkers and stray wakes (`/proc/sysstat` `w` lines, hw2 window)
15.1k poll wakes/s are delivered, and **9.6k/s of them go to tasks parked with `poll_mask = ALL`**:
| task | blocked in | mask | wakes/s |
|---|---|---|---|
| `login` pid 20 | read (sc 0) of console stdin | ALL | 3321 |
| leandros-sysbus `netctl-events` | read (sc 0) of /dev/netctl | ALL | 2968 |
| sshd `tokio-rt-worker` | epoll_pwait | ALL | 2777 |
| cosmic-panel worker 514 | epoll_pwait | 0xa7baad76a782306a (bloom ~60 % full) | 87 |

wakestat over the sw1 window: `net/lib.rs:4491` (unix send, 1440 calls/s, 3900 woken/s, 2600 allmask) and `net/lib.rs:5692`
(unix recv), `vfs/lib.rs:7501` (eventfd write), `vfs/lib.rs:7415` (pipe write). Each keyed wake also releases the broadcast
parkers. Epoll probes run at ~17k/s system-wide (12.5 per epoll call). RUN_QUEUE lock: 5.66M acquisitions, 1.62M contended,
18.2 s spin since boot.

Root causes of the three ALL parkers, in code:
- `login`: `kernel/src/syscall.rs:6399`. A blocking console-stdin read parks with `block_on_poll_prepare_until(now + 10 ms)`,
  which is broadcast.
- `netctl-events`: `kernel/src/syscall.rs:10557` `vfs_block_hint` falls back to `(POLL_TAG_ALL, +10 ms)` because
  `servers/vfs/src/lib.rs` `fd_wake_tag` has no arm for /dev/netctl. The producer already wakes a tag:
  `servers/net/src/netctl/mod.rs:145` `tag_of(open_id) = poll_tag(NETCTL, open_id)`.
- sshd: `kernel/src/syscall.rs:13035`. Net probes give only AF_UNIX-connected and connected TCP/UDP a tag ("the rest leave it 0 →
  broadcast"), so the TCP **listener** in tokio's epoll set makes the whole set park ALL.

## 4. Fixes, ranked by expected CPU saving
1. **Remove the three broadcast parkers (kernel; expected 20–25 % of a core, plus less RUN_QUEUE contention for everyone).**
   Their own sys time alone is 4.7 + 7.6 + 8.1 = 20.4 %.
   - `servers/vfs/src/lib.rs` `fd_wake_tag`: add the /dev/netctl node kind → `poll_tag(poll_class::NETCTL, open_id)`
     (the open id the node's read path passes to `do_read`).
   - `kernel/src/syscall.rs:6399` (blocking console read): park on a console-input tag plus `POLL_MASK_TIMED_ONLY` instead of ALL.
     Have the evdev/serial-drain producer wake that tag. The 10 ms deadline can stay as the backstop.
   - `servers/net/src/lib.rs` NET_POLL reply for TCP (and AF_UNIX) listeners: set data[32] with a per-listener key
     (`poll_tag(LISTEN, sock)`), and `wake_poll_key` it where a connection is queued for accept().
   - Check: rerun `zc/m.sh` and confirm that no `w` row has mask ALL with more than 100 wakes/s, and that sshd/login/netctl-events
     drop below 1 %.
2. **cosmic-comp + cosmic-panel epoll cost (kernel; up to ~25 %, realistically 10–15 %).** These are 21 % and 10 % on-CPU inside
   epoll_pwait: 368 µs per call for cosmic-comp, and ~0.45 ms per stray park for the panel (239 parks/s for 9 returns).
   This is `epoll_wait_ready` in `kernel/src/syscall.rs` (~11870 onward). Its re-probe cost is ~12 probes per call, each a VFS/NET
   round trip, and the panel's 64-bit bloom mask is too full to filter keyed wakes. Fix 1 removes part of the stray wakes.
   After that, profile which registrations the ready list re-probes per call (`ep_always`/ready entries), and widen the
   bloom filter or use exact keys for multi-fd sets.
3. **Video path (expected ≤ 5–8 %).** VA-API is already zero-copy; the remaining per-frame cost is RDD's PRIME export/close
   churn (sys 5.7 %) and the parent's per-frame EGLImage create/destroy. Firefox prefs worth A/B testing (not tested here):
   `gfx.webrender.compositor.force-enabled=true` (Wayland native compositor: the video goes as a dmabuf subsurface to
   cosmic-comp and skips the Renderer's YUV pass; that is part of the Renderer's 14 % and of the 63 % RCS busy). Make the change in
   `ports/firefox/leandros-prefs.js` only after a measured A/B. Kernel side: the close/recvmsg cost of SCM_RIGHTS dmabuf fds
   (`servers/net/src/lib.rs` fd transfer, dmabuf release in `drivers/src/drm_device_interface.rs`). Getting VP9 instead of H.264
   would not help: the decode is already ~0.5 ms/frame on vcs0.
