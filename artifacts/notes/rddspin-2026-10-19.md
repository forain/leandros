# rddspin 2026-10-19: the RDD "poll spin" is Firefox's frame-pool scan, not a kernel false-ready

Laptop, good kernel `#1 main-2d54349a`, fresh boot, session over greetd IPC at uptime 188 s. Eight YouTube launches (aqz-KE-bpKQ, VA-API
defaults), panel On in each, last window ending at uptime ~1040 s. Firefox ran with an LD_PRELOAD `poll()` census (scratchpad `rdd/pshim.c`). The shim names
callers with `dladdr` and fd kinds with readlink of the process's own `/proc/self/fd/N`; it does not read maps. A census window is 30–35 s, taken
+55..+85 s after RDD appeared. Data: scratchpad `rdd/a1..a8`, analysis `rdd/an.py`.

## What RDD polls
Every `poll` in RDD, in all eight launches, comes from one call site: `libxul.so+0x680b2a6`, `nfds=1`, `timeout=0`, `events=POLLIN`, on an
**eventfd**. That is `DMABufSurface::IsGlobalRefSet()`, the cross-process refcount of a VA-API frame. `VideoFramePool` calls it on every
surface in the pool for every decoded frame (GetFreeVideoFrameSurface / ReleaseUnusedVAAPIFrames). `wall == ns` in `/proc/sysstat`, so no
call ever parks.

- The ready rate is fixed by the frame rate: about 1.3k/s at 60 fps, the same in yt1 and yt2. The zero-return rate grows by about 124/s for
  each extra pool surface. yt1's 18.4k/s therefore fits a pool of about 150 surfaces. Firefox grows the pool whenever every surface is still
  held by the renderer (a startup or compositor stall) and never shrinks it while that decoder lives, so the pool size, and with it the poll
  rate, varies from launch to launch. 17–45 surfaces were seen here. The 19k/s case did not come back in 8 launches.
- **The kernel's answers are correct.** A return of 0 means the eventfd's counter is 0 (no holder). Ready means a holder exists. There is
  no POLLERR or POLLNVAL, nothing that stays ready, and no fence or syncobj fd in this loop. The vfstag "always-ready" static tags do not
  apply, because nothing parks.
- Our cost per call is 4.0–4.1 µs. At yt1's rate that is about 7.5 % of one CPU in poll, which is what makes the scan visible. A fast path for
  a single-fd, zero-timeout poll would cut it. It is optional and is not a correctness fix.

## A real eventfd bug found on the way (not the cause): EFD_SEMAPHORE is ignored
`servers/vfs/src/lib.rs` `handle_eventfd` keeps only `O_NONBLOCK|O_CLOEXEC` from the flags. The `VnodeKind::EventFd` read (around line 7279)
always returns the whole counter and resets it to 0. Under `EFD_SEMAPHORE` (flag 1) a read must return 1 and subtract 1.
Firefox creates the global-refcount eventfd with `EFD_SEMAPHORE` and drops one reference per read. On our kernel, the first release of a
frame with two or more holders therefore marks it free while it is still held. That can only under-report "in use": it can let the decoder
reuse a frame that is still on screen (possible flicker), but it cannot grow the pool, so it does not explain the spin. It needs its own small
lane: store the flag in the fd entry, return 1 and subtract 1 on a semaphore read, and add a regress test (create with initval 3 and
EFD_SEMAPHORE, then reads return 1,1,1,EAGAIN, and POLLIN stays set until the last read). After that fix, measure the pool size again,
because correct refcounts may keep more surfaces in use.
