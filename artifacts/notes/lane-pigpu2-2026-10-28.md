# lane/pigpu2 2026-10-28: Mesa v3d renders on the Pi 5

PARTIAL-to-FIXED: GLES on v3d renders; kmscube (scanout) has no display path yet.

Trial = main a28de2b2 rpi5 build, `v3d.probe=1`, pi-sync'd root.

Root cause of "GL falls back to softpipe": the Pi root was prepared with the virtio-pci
sysfs identity for card0/renderD128. pi-sync skips `/sys/dev/char/226:*`, so it never
changed. Mesa's loader finds `device/vendor` + `device/device` (0x1af4:0x1050), finds no
matching PCI id and picks softpipe. Vulkan (v3dv) needs `subsystem -> platform` only.
Fix on the Pi: `scripts/pi-v3d-sysfs.sh` (new) removes the PCI attributes, links
`subsystem -> bus/platform`, writes the v3d uevent. Needed once per root until pi-sync
carries /sys/dev/char/226:*.

Evidence:
    PASS ident subsystem=platform
    PASS armed auto
    PASS vulkan dev=V3D_7.1.10.2 api=1.3.328 fill ok 16384/16384
    PASS compute csd ok 4096/4096 renderer=V3D_7.1.10.2
    FAIL kmscube renderer=? failed to queue page flip: Operation not permitted
    pi-gpu-smoke: 4/5 PASS
    es31test PASS fbo crc=0x033e7e62 bad=0/65536 renderer=V3D_7.1.10.2
The same FBO test on softpipe (before the fix) gives the identical crc 0x033e7e62, so the
analytic image (blue clear, red quad on pixel centres [64,192)) is renderer independent.
New: `es31test --fbo` (ports/mesa/es31test.c).

Default-on verdict for v3d.probe: safe for boot; see the report. gpu-env has no v3d path, so
init's precheck prints "NO GPU RENDERER" and skips greetd/COSMIC. A desktop would need
(1) a `v3d` branch in ports/greetd/data/gpu-env (native GL, no zink), (2) a scanout path:
there is no bootloader framebuffer and no HVS driver; kms_v3d.rs copies BOs into the
firmware framebuffer, but hdmi hpd=0/edid refused with nothing attached and no fb was
allocated, hence kmscube's EPERM page flip; (3) cosmic on v3d GL, untested.
Open: pi-sync should carry the sysfs identity; kmscube needs a display.
