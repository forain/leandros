# sockspin: Firefox parent "Socket Thread" at 25-48 % CPU during YouTube (2026-10-18)

Laptop, kernel dbf20e6a-era (08be3f47 tree). Firefox already playing Big Buck
Bunny (aqz-KE-bpKQ): RDD busy (~11 % on each of 4 threads), panel On
(`blanktest --status`). Investigation only, nothing deployed or built.

## Evidence

Thread CPU over 10 s (`ab/an.py`, then `/proc/sysstat` `t` lines):
Socket Thread (tid 12739) 48 % in one window and 25 % in the next. In the second
window, 23 of its 25 points were **in syscalls** (`sys_ns`), not user code.

`/proc/sysstat` `w` line of the Socket Thread, on three reads:

    w 12739 12709 S 7 0xffffff01 0 0xffffffffffffffff 10794839278
    w 12739 12709 S 7 0xffffff01 0 0xffffffffffffffff  2474765265
    w 12739 12709 S 7 0xffffff01 0 0xffffffffffffffff  6928505948

It sits inside ONE `poll()` (nr 7) for 2.5-10.8 s at a time, as on Linux
(nsSocketTransportService polls with long timeouts), but parked with
`poll_mask = POLL_TAG_ALL`. **It is not a userspace spin**: no poll-returns-
ready/EAGAIN loop, no timeout-0 churn. The CPU is burned inside the kernel, in
the wake / re-probe / re-park loop of that one call.

Firefox parent, census per thread group (`s` lines, 10 s, per second; the
census is per thread group, not per thread):

| nr | syscall | calls/s | on-CPU µs/call | zero % | kernel CPU |
|---|---|---|---|---|---|
| 7 | poll | 956 | **476** | 32.6 | **45.5 %** |
| 16 | ioctl | 3573 | 20.7 | 98.8 | 7.4 % |
| 47 | recvmsg | 1130 | 59 | 0 | 6.7 % |
| 46 | sendmsg | 716 | 55 | 0 | 4.0 % |
| 202 | futex | 2076 | 13 | 50 | 2.8 % |
| 228 | clock_gettime | 17582 | 0.3 | 100 | 0.6 % |
| 24 | sched_yield | 3427 | 2.1 | 100 | 0.7 % |

On average a poll call stays on the CPU for 476 µs (blocked time is not
counted). That is the re-probe cost summed over the many wakes during one long
call. The recvmsg/sendmsg rates are QUIC: `/proc/net/udp` shows one uid-1000
socket `00000000:8709`, unconnected (state 07), plus two TCP :443. The
census's "zero" column cannot separate EAGAIN (negative) from success, and it
has no byte sizes, so the recv sizes are not measured here. The 0 % zero
returns on recvmsg only show that it never returned 0.

Poll-channel wakes, system-wide, from `/proc/wakestat` over 10 s: 8,733 wake
calls/s woke 22,977 tasks/s, and **12,010/s of those were broadcast-mask
(`allmask`) parkers**. Top wakers: `servers/net/src/lib.rs:4474` (AF_UNIX
data, 4,691 allmask/s), `:5675` (AF_UNIX space, 3,785), `servers/vfs:7492`
(1,810), `vfs:7406` (925). Only about 5 tasks are parked with a broadcast mask
(the Socket Thread, busd's epoll, an sshd thread, login on the console, pid
908), so the Socket Thread is woken an estimated ~2,000-4,000 times/s, about
once per AF_UNIX message anywhere on the desktop (Wayland, PipeWire, Firefox
IPC). Every wake re-probes the whole pollfd set about 3 times (once in
`poll_block`'s reprobe via `poll_any_ready`, once in the `poll_wait` loop, and
once in `poll_fds_mask` before the next park). Each probe is a NET_POLL/
VFS_POLL handler call that takes SOCK_TABLES and stack locks.

## Root cause

Firefox's HTTP/3 (QUIC) socket is `bind(0.0.0.0:0)`. Since lane udp2, every
wildcard UDP bind, port 0 included, becomes a `udpany` "wildcard server" with
a mirror socket on every stack (`servers/net/src/lib.rs:3434-3435` →
`udp_materialize(.., server=true)` → `udpany::create`, `:3945`). Its NET_POLL
answer returns **no tag**:

- `servers/net/src/lib.rs:6880-6897`: the `udpany::of(ofd).is_some()` arm ends
  in `(ev, Some(seq), None)`, and its comment says "Broadcast mask: a mirror's
  datagram wakes the mirror's own tag, which this socket does not report".
- `kernel/src/syscall.rs` `reply_poll_tag` (data[32] != 1 → `PollTag::ALL`).
  `poll_fds_mask` (:12782) ORs it into the set. `poll_wait` (:4295) then parks
  at :4341 with mask = all ones.
- `sched/src/lib.rs:2379-2385`: a broadcast mask is reached by EVERY wake.

The pipe (PollableEvent) and the two TCP sockets are tagged and keyed
(`vfs handle_poll` pipe keys; net :6952 `PollTag::keyed(inet_key)`). The one
untagged fd poisons the whole set.

A connected or single-stack UDP socket already reports
`PollTag::keyed(&[inet_key(sid, h)])` (:6952). The daemon wakes exactly
those keys for every socket whose readiness moved, mirrors included
(`readiness_moved` :3150-3170, `wake_poll_key` :3006). So the wildcard arm
can report the keys of all its per-stack sockets with no loss of wakes.

Other untagged (broadcast) NET_POLL answers to fix in the same pass: TCP
connecting (:6930 `return net_poll_reply(ev, None, None)`), TCP listeners
(:6971), ICMP (:6986), unbound UDP/ICMP (:6995, :6997), and the `_` catch-all.
They matter less here because they are short-lived or not polled by Firefox.

## Proposed fix (one small lane, "udpanytag")

1. In the `udpany` arm of `handle_poll` (`servers/net/src/lib.rs:6880-6897`),
   collect `inet_key(sd, h)` for every `(sd, h)` in `udpany::order(..)` and
   return `Some(PollTag::keyed(&keys[..min(3)], extra))`. `extra` is the OR of
   `sched::poll_key_bit(k)` for any keys past the third, kept keyless so they
   can never lose a wake (`PollTag::keyed` silently drops keys past 3; the
   laptop has lo+eth0+wifi0 = 3 stacks, but MAX_STACKS = 1 + MAX_NETIF).
2. Optional, same lane: give the TCP-connecting reply its keyed tag too
   (:6930).
3. Test: a QEMU/regress case that parks `poll()` on a socket from
   `bind(0.0.0.0:0)` plus a pipe. Check that its `w` line mask is not all ones,
   that a datagram arriving on any stack wakes it, and that unrelated AF_UNIX
   traffic does not (the per-task `pwakes` counter in newer kernels).
4. Laptop A/B under the playback rule. Expect the Socket Thread's CPU to fall
   from 25-48 % to a few %, `allmask` wakes in `/proc/wakestat` to fall by
   about 2-4k/s, and the parent's poll on-CPU µs/call to fall well below 476.

Secondary (separate lane, if still needed after the fix): a woken poll probes
the whole set about 3 times (`poll_block` reprobe + loop + `poll_fds_mask`).
Reusing the loop's probe results for the mask would cut each wake's cost by
about 2/3 for every poller.
