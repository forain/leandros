# lane/wifi2 — 2026-10-18

Laptop (HP EliteBook 840 G5, Intel 8265). Base: main 0a63f5cb. Goal: close
the "Open, Wi-Fi and network" items of TODO.md's laptop performance wave:
the poor link, the iwlwifi gaps, and the slow / late SSH boots.

## Measurement tool

`scripts/wifibench.py` (new): from the wired Mac (en0) against
`LEANDROS_REMOTE`. Per run N MB host -> guest (`ssh cat > /dev/null`) and
N MB guest -> host (`ssh head -c N /dev/urandom`), then `ping -c 50 -i 0.2`;
around it, deltas of `/proc/net/nic` wifi0 `rx_quality` (the AP's data
frames to us with the Retry bit = `ap_retry`) and `/proc/net/wifi`
`tx_retries` (our extra attempts per frame = `tx_retry`). Default 3 runs of
4 MB, the median is reported. It never reads /proc/cmdline.

Reading:
- **5 GHz is the fix for the poor link**: 5x down and up, a third of the AP
  retries, and no latency spikes, at a 3 dB weaker signal. On 5 GHz the AP
  sends us two-stream MCS 11-12; on 2.4 GHz MCS 2-4 single stream. The
  2.4 GHz channels are crowded (18 BSSs, several on ch 1 and 6).
- `txant=b`: no gain. Antenna B's uplink is much worse on ch 1 (1.5
  retries per frame, MCS0 9 % success) and slightly worse on 5 GHz (rc
  settles at MCS2 instead of MCS3). The downlink numbers vary run to run
  by 2x and do not depend on our TX antenna. Default stays automatic (A).
- `btcoex=wifi`: no gain (the baseline already had `bt_kill 0` and no `8a`
  statuses: BT coex was never killing our frames). Default unchanged.
- The ch 1 BSS of 'Anvara' (84:78:48:d8:7e:79, the same AP as 'Anvara 5G')
  is the worst: rate control falls to 1-5.5 Mb/s on uplink.
- At boot the manager picked 'Anvara' (the legacy profile wins a tie) on
  ch 1 in all three boots.

So the default change: autoconnect prefers a usable 5 GHz BSS (below).

## What changed (code)

| Area | Change | Where |
|---|---|---|
| Band preference | Autoconnect ranks (priority, this-boot recency, **usable 5 GHz** (ch > 14, >= -80 dBm), stored timestamp, legacy, signal). A network connected this boot still wins (NM's "go back to the last one"), but at boot a usable 5 GHz BSS beats the legacy 2.4 GHz profile. `wifi.prefer5=0` restores the old order. | `drivers/src/wifi_pref.rs` (host tested), `wifi_mgr.rs` `pick_auto` |
| TX aggregation | iwlmvm's path for the 8000 family: BSS queue reconfigured at association as an aggregation queue for TID 0 (SCD_QUEUE_CFG aggregate=1, window 64, SSN = ring write index) and our QoS sequence numbers start at the ring index (scheduler requirement; `misaligned` counts violations and realigns). ADDBA request once the link is up and the queue is empty; on success ADD_STA (STA_MODIFY_QUEUES / TID_DISABLE_TX) clears TID 0 and the LQ frame limit becomes min(63, window). A-MPDU TX responses (frame_count > 1) do not reclaim; BA_NOTIF reclaims to scd_ssn and feeds rate control (sent/acked). A single-frame failure on the session sends a BAR (ACK + TX_CMD_FLG_BAR, management queue). DELBA from the AP (recipient) sets tid_disable_tx again. No response in 1 s: retry twice, 10 s apart. The TX reclaim now ignores indices outside the frames in flight (iwl_pcie_reclaim's check). `iwlwifi.txagg=0`. | `drivers/src/iwl_agg.rs`, `iwlwifi.rs`, `iwl_cmd.rs`, `iwl_assoc.rs`, `iwl_trans.rs` |
| 40 MHz | 5 GHz only: the AP's HT operation names a secondary channel with STA width any, the AP's HT caps have 20/40, and NVM flags allow 40 MHz on both halves. PHY context width 40 + control position (iwl_mvm_get_ctrl_pos), HT caps 20/40 + SGI40 (rx_highest 150/stream), STA_FLG_FAT_EN_40MHZ, HT protection also in 20 MHz-protection mode, rate control over MCS/40 (rate_n_flags width bit, rs.c 40 MHz tables, initial MCS from signal - 3 dB). `BSS width:` boot log line. `iwlwifi.ht40=0`. | `wifi_ht.rs`, `iwl_cmd.rs`, `iwl_rs.rs`, `iwlwifi.rs` |
| WMM updates | A WMM Parameter element with a new set count in the tracked BSS's beacons (mac80211's rule) updates the MAC context EDCA (`ht:` line `wmm set N updates N`). | `iwlwifi.rs` `rx_mpdu`, `update_erp` |
| Statistics | STATISTICS_NOTIFICATION parsed (v13, 564 bytes: the firmware has API flag NEW_RX_STATS and no 0x9d CMD_VERSIONS entry). It arrives after every beacon (n 599 for 600 beacons). `/proc/net/nic` `fw_stats:` beacons, missed, average and per-chain beacon energy, raw beacon-silence values (not dBm on this firmware: -10773), channel load, CTS/ACK/BA timeouts, RX/TX/on air time; plus our per-chain beacon EWMA from the RX PHY info. On 2.4 GHz ch 6 `cts_timeout 8115 ack_timeout 8318` against 877 / 334 on 5 GHz: the 2.4 GHz channel is the problem. | `iwl_cmd.rs` `parse_stats_v13`, `iwlwifi.rs` |
| Rate control | Antenna comparison: every 30 s (sooner, at most every 5 s, when the other chain's beacon EWMA is 6 dB stronger) move to the other antenna at the same rate for >= 1 s and a valid window; keep it at >= 125 % of the old throughput, else restore antenna, rate and windows. Restart after idle: the first TX outcome after all windows went stale re-seeds the rate from the current beacon signal. With TX aggregation the expected-throughput tables use rs.c's AGG columns; `on_ampdu` counts BA notifications. | `iwl_rs.rs` |
| Bench | `scripts/wifibench.py` (above). | |

At boot the manager now picks 'Anvara 5G' (`connecting to 'Anvara 5G' ... [auto]`), runs 40 MHz

Against what the laptop used to get (2.4 GHz): about 8x down and 5x up. Against the same 5 GHz BSS
on the old kernel: +55-65 % down, +0-25 % up.

Sparse pings (1 s apart, Mac -> laptop) lose 1-4 % on every kernel: good kernel 2.4 GHz 3/90,
good kernel 5 GHz 5/290, lane 5/200, lane ht40=0 4/90. Not a regression; every lost ping's reply
side shows no TX failure (`tx_counts` enq == ok), so the requests are lost before us. Not chased
further (new TODO item).

Antenna comparison on the laptop: 3-11 probes per bench, about half kept with the first 10 %
margin (the antennas are close and 2.4 GHz is noisy), hence the final 25 % / 1 s.
